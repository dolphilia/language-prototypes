# 実際の直接呼び出しへ保証をつなぐ

**E5の実装・証明・測定・[完了監査](calls-audit.md)が完了した。** 検査付きの呼び出し元E3bとM2全体は未完了。

[証明と実機の集約](calls-verification.json) · [証明の入力](calls-proof.json) · [前提の供給元](calls-assumptions.json) · [固定した測定方法](calls-protocol.md)

## 何を接続したか

24バイトの`vp2_call_copy`から、M1の76バイトの`vp2_memcpy_chunk8`を一度だけ直接呼ぶ。呼び出し元はSPを16バイト減らし、枠内へLRを保存し、`BL`、LRの読み戻し、SPの復元、`RET`を実行する。呼び出し先は従来どおりスタックを使わない。

| 配置 | 呼び出し元の相対位置 | コピーの相対位置 | BLの変位 | コード束 |
| --- | ---: | ---: | ---: | ---: |
| a | 0 | 24 | +16 | 100バイト |
| b | 332 | 0 | −340 | 356バイト |

配置bの余分な256バイトは、配置を変える実験のNOPである。配布する処理に必須の容量ではない。

対象は、一つの外部`ARM64_RELOC_BRANCH26`、PC相対、4バイト、加算値ゼロに限定した。オブジェクトの参照が許可したシンボルかを確認した後、リンク結果の`BL`を読み、その**実際の到達アドレス**がコピー本体の先頭と等しいことを確認する。同じ名前だけでは受理せず、呼び出し先の全76バイトも照合する。Mach-Oの独自抽出器とLLVMのシンボル位置を比較した。

## 証明が扱う範囲

リンク済み実行ファイル内の呼び出し元・コピー・間のNOPを一つのコード束として取り込む。既存の基盤の取り込み関数は実行ファイルを拒否したため、実物の指定範囲をそのまま読み、期待する命令語と照合する小さな取り込み処理を追加した。実行ファイルのヘッダーをオブジェクトに偽装する処理はしていない。この追加処理とファイル位置の対応は未検証の境界として記録する。

HOLではコピーが束内へ完全に埋め込まれていることを確認し、実際の`BL`をステップ実行した後、M1のコピーの定理を使う。コピー本体を親で再シミュレーションして正しさを主張する構成ではない。親が実行するのはスタック操作と呼び出し・復帰の命令である。

共通ロード位置`pc`を量化し、相対位置を保つ配置を対象にした。Mach-Oの望ましいVMアドレス一つに固定した証明ではない。コード束と出力・専用スタックが重ならず、スタックと入力・出力が分離しているという条件から、コピーの入口条件を導く。

正常な呼び出しについて、次を別々の契約で確認した。

- 出力が開始時の入力と等しく、有限ステップで元の復帰先へ戻る。
- SPとLRを復元し、許可した一時レジスタ・フラグ・イベント・出力・16バイトの枠以外を保存する。
- 途中の読み取りは入力と専用枠、書き込みは出力と専用枠の内部にある。最終状態の保存だけから途中のアクセスを推定しない。
- 両配置に、コードが実際にロードされ公開条件を満たす具体的なモデル初期状態が存在する。

33個の閉じた定理と反例を新規プロセスで317.5秒かけて検査し、期待する命題・空の仮定リスト・追加公理なしを確認した。この中には再利用するM1の14定理を含む。保存したJSONを定理として読み込んでいない。

## 拒否と反例

再配置の種別・PC相対・幅・外部指定・シンボル・位置・加算値、分岐範囲、同名の別実装、誤ったリンク先、実際の中継スタブ、動的libcへの接続など、23例を拒否した。取り込み境界でもヘッダー・アーキテクチャ・arm64e・種類・範囲・整列・期待する命令語の改変の9例を拒否した。これらは成果物の不一致や未対応形式の拒否であり、意味論上の反例とは分ける。

呼び出し元の誤実装は、同じコピー本体を使う別の実行ファイルとして用意した。

| 誤実装 | モデルで確認した違反 | 実機の観測 |
| --- | --- | --- |
| SPを32バイト減らして保存 | 有効な初期状態から2ステップ後、許可した16バイト枠外へのストア | 枠の下の番兵を破壊 |
| X19を0へ変更 | 17ステップ後に復帰するが、保存すべきX19が変化 | ABI検査で検出 |
| LRを0へ変更 | 17ステップ後、SPは復元するがPCが元の復帰先と異なる | 分離した子プロセスで異常終了 |

それぞれに、同じ引数の正常版が通る対照がある。モデル内では初期状態・公開条件・必要な数値条件を閉じた定理として検査した。失敗したタクティックや実機の異常終了だけを、HOLの一般のHoare命題の否定と同一視していない。

正常版の実機チェックは各配置10,944件で、内容・入力の保存・戻り値・ABI・SP・16バイト枠の両隣の番兵を調べた。

## 呼び出しの速度と容量

[42ケース・各7プロセスの測定](calls-measurements.md)では、直接版に対し、配置aは高速1・低速26・不明15、配置bは高速0・低速27・不明15だった。短い長さでは実際の呼び出しと保存・復元の費用が見えた。次は整列済みの例で、ns/呼び出しの中央値である。

| 長さ | 直接 | 呼び出しa | 呼び出しb | libc |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 1.569 | 2.218 | 2.241 | 1.598 |
| 8 | 1.928 | 2.570 | 2.570 | 1.935 |
| 64 | 4.821 | 5.499 | 5.484 | 2.164 |
| 256 | 12.859 | 13.515 | 13.456 | 4.911 |
| 4096 | 176.331 | 174.469 | 177.704 | 54.413 |

ループ・間接呼び出し・添字計算も測定に含むため、差を`BL`単体の遅延とは解釈しない。長いケースの逆転もあり、配置・キャッシュ・測定変動等を含む観測から呼び出しによる一般的な高速化は主張しない。

呼び出し元24バイト、コピー76バイト、専用枠16バイトで、証明用の実行時処理はない。M1のコピーと埋め込み・E4のmemmove・呼び出し元の本体合計は196バイト。測定用実行ファイル全体はaが34,064、bが34,160バイトで、Cの測定器やメタデータを含む。配置の256バイトの差がファイル全体へそのまま加算されるとは限らない。

## 軽くなった負担と、残る前提

| 対象 | 変化 |
| --- | --- |
| 関数を組み合わせる側 | コピーのループの証明を再利用できる。子への復帰先を独立した仮定として与えず、実際の`BL`から導ける |
| 呼び出し元の実装者 | 枠の分離・整列・保存と復元、親子の変更範囲、イベントを接続する作業が増える |
| ビルド環境 | リンカを無条件に信用せず、対象のリンク結果を検査できる。代わりに、範囲抽出・バイト照合・証明入力の管理が必要になる |
| 実行時 | 証明用コードやデータは不要。実際の呼び出しと16バイト枠の費用は生じる |
| 外部契約 | 通常RAMとスタックの物理的な有効性・寿命・排他的利用、モデルとCPU、OSが検査したバイトを共通の相対位置で配置することは残る |

汎用の検証済みリンカ、動的・間接呼び出し、OSやアロケータの検証は達成していない。E3aの検査条件を実際の分岐と引数生成へ接続する作業が、次のE3bである。

```sh
python3 prototypes/verified-libc-evolution/tools/verify_calls.py
python3 prototypes/verified-libc-evolution/tools/measure_calls.py
python3 prototypes/verified-libc-evolution/tools/audit_calls.py
```

M1の完了とE3aの契約固定を前提としたE5単独の入口であり、M2全体の完了とは区別する。
