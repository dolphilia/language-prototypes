# 重複コピーで確認できたこと

[完了監査](memmove-audit.md) · [全測定値](memmove-measurements.md) · [証明と実機の集約](memmove-verification.json)

**非重複という入口条件はアルゴリズムと証明で取り除けた。一方、バイト単位の実装は、実際にデータを移す多くのケースでlibcより遅かった。** E4の実装・証明・評価は完了したが、汎用的な性能優位は得られていない。

## 軽くなった負担と、増えた作業

| 対象 | 変化 |
| --- | --- |
| 呼び出し側 | `memcpy`とは異なり、入力と出力が重ならないことを証明する必要がない。同一アドレスも受け取れる |
| ライブラリ側 | 方向を正しく選び、まだ読んでいない部分が壊れないことを証明する必要が生じた |
| 仕様 | 出力は開始時の入力と等しい。重複時に入力全体が不変であることは要求しない |
| 証明の再利用 | ロードとストアは、既に証明したバイトコピーの部品を使う。前向き・後ろ向きの不変条件と接続は新しく作った |
| 実行時 | 追加の証明処理・専用スタック・ヒープは不要。本体68バイト。ゼロ長と同一アドレスはデータへアクセスしない |
| 未解決の負担 | 普通のRAMの有効性・寿命・排他的更新は呼び出し側の契約に残る。E3aの二つの非重複の借用を、そのまま重ねてよいわけではない |

前向きでは未読の末尾、後ろ向きでは未読の先頭を保つ。これにより、既に読み終えた入力が出力によって変わっても、次の読み取りには影響しない。終了・戻り値・保存状態と、途中のデータアクセスは別に検査した。

42個の閉じた定理を新規プロセスで248.0秒かけて検査し、追加公理はなかった。実機35,709件と、方向3例・欠落2例・ゼロ長の減算・過剰な読み書きの8例を調べた。誤実装には有効なモデル初期状態からの有限の違反と、実機での違反・元の実装の正常対照がある。

## 速度は、証明の有無だけでは決まらない

303ケースのlibc比の分類は、高速95・低速195・不明13だった。高速の件数には、データを動かさずに返るゼロ長・同一アドレスも含む。件数だけを、転送性能の優位と解釈しない。

次は元のずれ0、コピー先との差+1での例。ns/呼び出しの中央値であり、ハーネスの間接呼び出し・ループ等の費用も含む。

| 長さ | 新版 | libc | 観測した結果 |
| ---: | ---: | ---: | --- |
| 0 | 1.278 | 1.588 | 新版が高速。データアクセスなし |
| 8 | 4.763 | 2.209 | 新版が低速 |
| 64 | 22.530 | 3.027 | 新版が低速 |
| 4096 | 1361.816 | 58.105 | 新版が低速 |
| 1MiB | 383250.000 | 38000.000 | 新版が低速 |

同一アドレスの4096バイトでは、新版1.249ns、libc1.557nsだった。この経路もデータを転送していない。大きな領域は128MiB以下の作業領域を回して測ったが、コールドキャッシュや実時間の上限は保証していない。CPU名の取得が環境に拒否されたため、アーキテクチャと診断を記録した。

本体68バイト、M1の2関数を含む本体合計172バイトに対し、容量用実行ファイルはそれぞれ33,592・33,752バイトだった。後者には起動コード・ヘッダー・署名等も含む。libcの共有コードを同じ方法で数えた比較ではない。

今回の結果は、形式証明に実行時の費用が必須ではないことと、速いアルゴリズムを選ぶ作業が別に必要なことを示す。ワード・SIMD・未整列アクセス・より適切な分岐への拡張は、その命令モデルと境界条件を検証した上で行う。E4の性能結果を理由に、今回の範囲を無制限に広げない。

```sh
python3 prototypes/verified-libc-evolution/tools/verify_memmove.py
python3 prototypes/verified-libc-evolution/tools/measure_memmove.py
python3 prototypes/verified-libc-evolution/tools/audit_memmove.py
```

これらはE4の入口であり、E5・E3bを含むM2全体の完了とは区別する。
