# 検査からコピーの入口条件を導く呼び出し元

> 本文の数値・経緯は初回の実装時の記録で、当時の段階の状態を含む。[保存した記録](../history/pre-final-integration-20261109/m2/split-result.md)と区別し、現在の結果は[監査](split-audit.md)・[全測定値](split-measurements.md)・[M2全体](audit.md)を参照する。

**E3bの実装・証明・実物・測定と[評価の監査](split-audit.md)が完了した。** [M2全体の統合と監査](audit.md)も完了した。

[検査結果](split-verification.json) · [64定理の入力](split-proof.json) · [前提の供給元](split-assumptions.json) · [事前に固定した測定方法](split-protocol.md)

```c
int vp2_copy_split(void *arena, size_t L, size_t split, size_t n);
```

一つの所有領域の先頭`n`バイトを、後ろの部分の先頭`arena+split`へコピーする。`0 < split < L`、`n <= split`、`n <= L-split`を実際の命令で検査し、成功なら0、不正なら1を返す。不正な場合は領域を変えず、コピーへ進まない。

## 呼び出し側から取り除けた条件

公開事前条件に、成功する`split`・`n`を要求していない。任意の`size_t`値について、実装の分岐を証明した。成功するときだけ、次を導いてM1のコピー定理へ接続する。

| 導く条件 | 根拠 |
| --- | --- |
| 分割が元領域の内部にある | 最初のCBZと符号なし比較 |
| 入力と出力の容量が足りる | `n <= split`と`n <= L-split`の比較 |
| 減算を容量として解釈できる | `split < L`を確認してから`L-split`を計算 |
| アドレスが折り返さず、両方とも元領域内 | 所有する根の非折り返しと、成功した範囲の条件 |
| 入力と出力が重ならない | 入力長が分割位置以下であること |
| コピーがコードや保存したLRを壊さない | コード・スタックと元領域の分離、および部分領域の包含 |
| 子から親へ戻る位置 | 実際の`BL`が設定するLR |

**元の領域が実際に`L`バイト有効で、生存し、排他的に利用できることは、依然として呼び出し側の契約である。** 整数の`L`を渡しただけではRAMや所有権は生まれない。これを検査したことにして、無条件の安全性を主張しない。

## 実際の命令と公開契約

呼び出し元80バイトとM1コピー76バイトを、リンク後の156バイトの束として取り込んだ。親の先頭は相対位置0、コピーは80、呼び出し命令は52、実際の変位は+28バイトである。共通ロード位置は量化し、成果物のバイトと相対位置を検査した。

成功経路の検査の後でだけ、SPを16バイト減らしてLRを保存し、引数を作り、コピーを呼ぶ。復帰後はLRとSPを戻して0を返す。公開契約は開始時の入力、有限復帰、戻り値、ABIと変更範囲を扱う。出力の外と別枠の専用スタックの外の保存はフレームへ残した。

不正値には4経路がある。分割位置ゼロ、末尾以上、入力側の容量不足、出力側の容量不足である。どの経路も、SPの減算・部分領域のアドレス生成・コピーを実行せず、データアクセスなしで1を返す。領域の内容とSP・LRを保存する。

途中のアクセスは機能とは別の契約で証明した。成功時の読み書きは元の所有領域と16バイトの専用枠の内部、不正値の経路は読み書きとも空である。最終状態の保存だけで途中の安全性を済ませていない。

## E3aの権限との接続

実際の機械語の事後条件を拡張し、**成功の戻り値0から、同じ`L`・`split`・`n`に対する借用・使用権限・返却を導く**定理を作った。先頭側の読み取り借用と後ろ側の書き込み借用を作り、借用中は全体の所有者の使用を止め、返却後に再開できる。

これは、機械語の成功条件と所有領域の論理を接続したものである。台帳が実メモリに対応すること、一つの現行台帳を逐次的に受け渡すことは契約に残る。一般の借用検査器・並行所有権の併合・実行中のOSによる失効を検証したものではない。失効後の使用を拒否するE3aの定理も同じ新規セッションで再検査し、不正な寿命のポインタを実機へ渡す試験にはしていない。

## 検査結果と反例

64個の閉じた定理と反例を、新規プロセスで347.5秒かけて検査した。M1の14定理、E3aの26定理、呼び出し元と領域の接続7定理、正例・誤実装の初期状態と数値条件・有限の実行17定理を含み、追加公理はない。実機では184,572件を検査した。短い領域の全組み合わせ、境界長、整列のずれ、最大の`size_t`値、戻り値・領域全体・ABI・SP・専用枠の番兵を含む。

| 誤実装 | モデルでの具体的な違反 | 実機の観測 |
| --- | --- | --- |
| `split < L`を省く | `L=16, split=17, n=0`で、25ステップ後に成功として返る | 正常版は1、誤実装は0 |
| `n <= split`を省く | `L=16, split=4, n=8`で、65ステップ後に成功として返る | 正常版は1、誤実装は0 |
| 出力側の長さ検査を省く | `L=16, split=12, n=8`で、42ステップ後に元領域の外へストア | ガードページで検出 |
| `L-split`を逆に計算する | 同じ入力で、42ステップ後に元領域の外へストア | ガードページで検出 |
| 出力を元の先頭にしてしまう | `L=16, split=8, n=1`で、33ステップ後の本来の出力が開始時の入力と異なる | 内容の比較で検出 |

いずれも元の公開事前条件を満たす初期状態を構成し、必要な数値の分離や整列も閉じた定理として証明した。誤実装がM1コピーの非重複条件を満たさないケースでは、その定理を使い回していない。実際の命令の有限実行が違反の根拠である。実機には同じ引数で正常版が通る対照がある。

減算を早く計算すること自体が常に誤りとは限らない。結果を使う前に正しい条件を検査すればよい場合もある。今回の誤実装は、必要な範囲条件の省略による折り返しの誤用や、減算内容の誤りであり、命令順序の違いだけを反例と呼んでいない。

## 速度と容量

[全測定値](split-measurements.md)では、正常な42ケースの直接版比は低速25・不明17、単純呼び出し版比は全42ケースが不明だった。同じ一つの領域を使い、各変種を7個の別プロセスで測定した。次は元のずれ0の例で、ns/呼び出しの中央値である。

| n | 直接コピー | 単純呼び出し | 検査付き |
| ---: | ---: | ---: | ---: |
| 0 | 1.563 | 2.201 | 2.184 |
| 8 | 1.869 | 2.488 | 2.499 |
| 64 | 4.708 | 5.319 | 5.317 |
| 256 | 12.158 | 12.769 | 12.776 |
| 4096 | 173.203 | 175.507 | 174.545 |

不正値の6経路の中央値は1.243〜1.251nsだった。これらはコピーを呼ばない経路である。正常値で検査の追加費用を判別できなかったことは、検査命令が消えたことや、任意のCPUで費用がゼロであることを意味しない。ループ・間接呼び出し・引数設定・配置を含む観測から、個々の比較命令の時間は切り出せない。

本体はコピー76、単純呼び出し24、検査付き呼び出し80バイト。埋め込み28とmemmove68も含めた全5関数は276バイトである。M1の2関数104バイトの予算とは別に数える。専用枠は呼び出し元ごと16バイトで、コピー自体は枠を使わず、最大使用は16バイト。証明のための実行時処理はない。

容量用の同じbasenameの実行ファイルは、直接版33,608、単純呼び出し版33,704、検査付き版33,704バイトだった。本体の差がファイル全体の差へそのまま表れるとは限らない。オブジェクト・配置余白・メタデータ等は生データへ分けて記録した。

## 軽くなった負担と、増えた作業

利用者は`split`・`n`がコピー可能かを重複して証明せず、戻り値で扱える。一方、ライブラリ側には分岐・符号なし演算・部分領域の包含・引数の入れ替え・ABI・スタック・権限を接続する証明が増えた。所有領域の根と実メモリの対応は消えていない。

可変のワードオフセットを含むアドレスは、既存の自動化だけで同じ非重複の事実を再利用できない箇所があった。部分領域の包含を明示的な補題にし、証明済みの等式で出力アドレスに名前を付けて接続した。この追加作業は証明器の支援の問題であり、ソフトウェアでは原理的に解消できない限界とは区別する。

```sh
python3 prototypes/verified-libc-evolution/tools/verify_split.py
python3 prototypes/verified-libc-evolution/tools/measure_split.py
python3 prototypes/verified-libc-evolution/tools/audit_split.py
```

前提はM1、E3a、E5の完了である。この単独の入口の通過と、M2全体のコマンド・完了監査は分けて記録する。
