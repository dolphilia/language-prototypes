# 独立した証明検査の最小実験

状態: **E6bの実現性調査は完了。独立再検査機能は未達**。M3全体の完了とは分けて記録する。

## 比較した二つの経路

| 経路 | 出力と再検査の方法 | 今回の判断 |
| --- | --- | --- |
| HOL Light同梱のProofrecording | 定理に証明オブジェクトを持たせ、`EXTENDED`ではXMLへ定義・推論等を出力する。別の検査器への入力が必要 | 固定済みソース内にあり、変更を共有環境へ持ち込まず最小実験できるため、こちらを実行した |
| OpenTheoryのHOL Light proof logging | HOL Lightの出力用インターフェースからarticleを作り、別のHOL実装やOpenTheory処理系が読む | 形式が標準化されている。一方、現在の標準カーネルへ出力コマンドを加えるだけでは動かず、logging版との統合と依存する定義・定理の輸送が必要 |

Proofrecordingの仕様は固定したHOL Lightの`Proofrecording/README`と`diffs/`を調べた。OpenTheoryの導入・出力APIは[公式FAQ](https://www.gilith.com/opentheory/faq.html)、推論・定義・型の表現は[article仕様](https://www.gilith.com/opentheory/article.html)に従う。両者の出力形式は異なり、そのまま交換できるとは扱わない。

## 入力と実際の試行

HOL Lightは`078839ea84531bd6c6cec9a58ebf69ba37149e0e`、OCamlは5.1.0。共有した証明器のソース・ビルド・パッケージは変更せず、`git archive`で発展版の`build/recording-trials/<nonce>/`へ取り出した。調査の実行費用は約1.75秒であり、移植・依存の輸送を実現する費用の見積もりではない。

対象は既存の`probe_ret.o`の一命令`0xd65f03c0`と、`VP_PROBE_RET_CORRECT`である。PCとX30の初期条件から、RET後のPCが復帰先になるという`ensures arm`の定理を出力しようとした。対象オブジェクトと証明ソースのハッシュ、コマンド、診断は[trial.json](trial.json)、出力要求は[ret-export.ml](ret-export.ml)へ保存した。対象の命題を新しい公理として登録する処理は含めていない。

1. 定理名を付けるJavaツールを構築し、jarを所定の`tools/`へ配置した。
2. 文書の手順に従って`Proofrecording/hol_light/`で`make`を実行した。定理名の変換は進んだが、旧`pa_j_*.ml`群が存在せず、`pa_j_3.07.ml`を生成する依存を解決できず停止した。[再試行のログ](e6b-recording-build-after-jar.log)。
3. RETの出力要求を渡して起動も試した。旧`hol.ml`の`or`がOCaml 5.1.0では未定義となり、論理をロードする前に失敗した。したがって`save_thm`と`export_saved_proofs`も未定義だった。[起動ログ](e6b-recording-startup.log)。

**プロセスの終了値は0だったが、ログにはエラーがあり、出力ファイルは0件だった。** 終了値だけでは成功と判定できない例でもある。RETの定理を記録版で証明・出力できたとは扱わず、別カーネルによる正例の確認も、破壊した証明の拒否も未実施である。

既存版の導入と検査を済ませた環境で、次を実行すると新しい隔離ディレクトリから再試行する。ネットワーク接続や共有環境への変更は行わない。診断が既知の非互換性と異なる場合は、任意の失敗を調査完了にせずエラーにする。

```sh
python3 prototypes/verified-libc-evolution/tools/independent_recheck.py
```

## 何が足りないか

| 項目 | 現在の対応と必要な作業 |
| --- | --- |
| 型と項 | 同梱の旧記録版は`type.ml`・`term.ml`の分離を前提にするが、固定した現行ソースではそのファイルがない。現行の`fusion.ml`に合わせた移植が必要 |
| 定義と型定義 | 定数の保守的定義、型定義の証明、型・項の置換を、記録側と検査側で一致させる必要がある。単に同名の定数を宣言して済ませない |
| 公理 | 受理してよいHOLの基礎公理を固定し、依存する公理を出力・検査する必要がある。輸送対象のRET定理を公理で与えることは許さない |
| 推論 | 旧`thm.ml`は基本推論と証明オブジェクトの生成を結び付ける。現行カーネルへの対応と、定理の構造比較を使う周辺処理の互換性を確認する必要がある |
| ARMモデルへの依存 | RETでも、機械状態、成分、ワード、デコード、遷移、`ensures`等の定義と使用定理が必要。最終命題の文字列だけでは再検査できない |
| 独立した検査器 | 出力形式・版を固定した検査器、全依存の対応、正常な証明の確認と改変拒否が必要。今回はその前段階で停止した |

OpenTheoryでは`axiom`コマンドが外部の定理への参照にも使われる。そのため、記事が読み込めたことだけでは十分ではない。import集合を点検し、輸送対象を含む未証明の命題が入り込んでいないことを確かめる必要がある。[article仕様の公理と外部参照](https://www.gilith.com/opentheory/article.html)。

## この結果の意味

今回の不成功は、固定した環境に同梱される旧経路を、そのまま使用できないという結果である。独立再検査の一般的な不可能性は示していない。現行カーネルに対応した記録機構の導入、依存の輸送、検査器の固定を行えば改めて試せる。

独立検査に成功しても、共有する仕様・ARMモデルと実機の対応、OS・ローダーの振る舞い、検査器の実行環境への信頼は別に残る。現在のM1の証明は従来のHOL Lightカーネルで検査しており、この予備実験によって信頼の根を減らしたとは主張しない。
