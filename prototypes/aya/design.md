# Aya 0.1の設計判断と検証計画

[概要](README.md) · [言語仕様書](spec.md) · [調査メモ](../../docs/notes/README.md)

状態: **設計草案**。作成日: **2026-11-07**。

本書は仕様の動機と実装・検証の順序を説明する。言語の受理・拒否を定める規範部分は[仕様書](spec.md)に置く。ここで挙げる既存研究の安全性証明が、そのままAyaへ適用されるとは主張しない。

## 1. 組み合わせ方

### 1.1 日常のコードに、すべての仕組みを要求しない

Ayaは三つの層に分ける。

| 層 | 主な機能 | 利用者が考えること |
| --- | --- | --- |
| 通常の値 | Value、明示的なmove/copy、read/inout | 値の独立性、変更する場所、所有の移譲 |
| 共有する構造 | domain、CellRef、Key | どの共有状態を、どの権限で読む・変更するか |
| 外部との接続 | contract、Session、binding | 相手に要求する条件、根拠、利用権限 |

多くの関数は第一層だけで書ける。共有するグラフが必要な部分だけ第二層へ、外部の実装や装置を扱う部分だけ第三層へ進む。

### 1.2 調査との対応

| 調査した考え方 | 採用した点 | 初版で絞った点 |
| --- | --- | --- |
| Rustの所有権・借用 | 移譲、初期化状態、共有読み取りと排他変更 | 第一級の借用参照と複雑な生存関係を持つ型は導入しない |
| Hyloの可変値意味論 | 独立した値、一時的アクセス、view、アクセス規約 | スカラーや固定長構造のCopyは暗黙複製を認める。method bundleは後続版 |
| GhostCell | データの参照関係と変更権限を、ブランドで対応付ける | domainはタスク内に限定し、領域回収でセルの寿命も整理する |
| OxCamlのモード | 局所性・利用回数・移譲可能性を分け、捕捉や内容へ制約を伝える | すべてのモード軸やmodalityを再現せず、所有・型の特性も併用する |
| 領域管理 | まとめて回収し、領域外への依存を検査する | セルの個別削除、可変グラフの一般的なGCは後続版 |
| 効果とケイパビリティ | 行いうる操作と、操作対象への権限を分ける | 行多相は持つが、汎用の効果ハンドラは導入しない |
| typestate・セッション型 | 状態を持つ資源を、所有の移譲として表す基盤 | 任意の通信プロトコルを生成するDSLは後続版 |
| unsafeと外部契約の考察 | 未検証の前提を接続設定へ集中する | native接続の初期プロファイルは同期的なバイト列操作に限定する |
| 形式検証の研究 | 規則と基本操作の証明義務を明示する | 汎用のユーザー向け証明言語を初版へ積み込まない |

## 2. 意図的に分けた性質

### 2.1 ValueとCopy

`Value`は意味上の独立性、`Copy`は暗黙複製の許可を表す。動的な配列はValueだがCopyではない。セルハンドルはCopyだがValueではない。

この区別がないと、すべてを暗黙コピーして性能を読みづらくするか、ハンドルの複製をデータ全体の複製と誤認させることになる。

### 2.2 所有と、クロージャの呼び出し回数

所有する配列を捕捉した関数でも、読むだけなら何度も呼べる。反対に、一回の呼び出しで所有資源を返すなら、その関数は消費される。

捕捉したものが一意か、関数を何度呼べるか、関数値を複製できるかを、同じ性質として扱わない。

### 2.3 不変な束縛と、共有される状態

不変なセルハンドルを持っていても、対応するキーによってセルの内容を変更できる。したがって、不変な束縛だからValueやSyncになるとはしない。

通常のValueなデータと、明示的な同一性を持つ資源を分けることで、可変値意味論を言語全体への曖昧な宣伝ではなく、型が満たす具体的な保証にする。

### 2.4 効果と純粋性

`!{}`でも、inout引数の変更はできる。一方、外部I/Oは効果と権限の両方を必要とする。

初版では「どんな副作用もない純粋関数」という別の概念を導入せず、インターフェースに見える変更権限と、追加の実行効果を区別する。

### 2.5 接続の権限と、相手への信頼

Sessionがあることは、誰が外部操作を使えるかを表す。相手が契約を守る証明ではない。

未検証native接続の保証は条件付きである。外部の違反からも内部を守るには、隔離や制約の強制について別の根拠が必要になる。

## 3. 共有領域の代償

### 3.1 権限をdomain単位にする

同じKeyから読み取りと変更を同時に許さないため、セルごとの実行時借用フラグを基本規則には必要としない。その代わり、別々のセルでもアクセスが連動する。

初版では、キーを分割する機構まで導入しない。逐次処理で十分か、独立したdomainへ分けられるかを、まず実際のプログラムで評価する。

### 3.2 セルを個別に解放しない

domain内では、ハンドルがどこに複製されたかをたどって解放する必要がなくなる。循環グラフも、領域終了で回収できる。

代わりに、使わなくなったセルの領域を途中で回収できず、領域の寿命が長いと使用量が増える。個別削除が必要な場合は、世代付きIDの検査、所有をたどる回収、管理されたGCなど、別の設計が必要になる。

### 3.3 domainは初版では移譲しない

グラフと権限をまとめて別タスクへ渡すことは有用だが、ブランドの封じ込め、隠れたハンドル、キーと所有者の一致などを追加で定める必要がある。

そのため、初版の並行処理は、通常の所有値、不変なShare、チャネルに絞る。共有グラフを別タスクで読み書きする機能が、既存のSend規則だけで自動的に実現されるとはしない。

## 4. 外部契約を狭く始める理由

同期的な呼び出しでは、借用の期間を呼び出しへ閉じ込められる。一方、DMAやコールバックでは、関数が戻った後にも外部のアクセスが続く。

保持を許す機能を追加するなら、転送中の所有、完了、停止、キャンセル、失敗時の保留まで一体として定義する必要がある。終了処理が必ず実行されることや、タイムアウトしたことだけを、返却の根拠にしてはいけない。

外部のプロファイルを後から増やせる設計にはするが、現時点で一般化したふりはしない。最初の実装対象は`sync_bytes`である。

## 5. 安全性を確立するための証明義務

以下は未達の検証計画である。

| 領域 | 必要な根拠 |
| --- | --- |
| 所有・初期化 | 移譲・代入・分岐・終了を通じ、読む場所が初期化済みであり、所有する格納を重複回収しない |
| 借用 | readの期間に競合する変更がなく、inoutの期間に重なるアクセスがない |
| view | yieldした格納が有効で、再開・早期脱出時も借用と終了処理が整合する |
| Value・copy | コピー後に観察可能な共有可変状態を作らず、内容を保つ |
| 局所性 | 格納・捕捉・抽象化を通じ、終了する領域への依存を持ち出さない |
| domain | 新鮮なブランド、キーの非複製、セルの安定した格納、領域回収が両立する |
| 構造的な型特性 | フィールド・クロージャ・抽象型を通じ、Send/Syncなどの根拠を失わない |
| タスク | 子へ移譲した所有を親で使わず、正常なscope終了までにすべての子を待つ |
| 効果 | 呼び出し、捕捉、正常な脱出、資源の終了処理の効果が上限から漏れない |
| 外部アダプター | wireと内部型の変換、範囲、ピン留め、利用期間の規約を満たす |
| バックエンド | 最適化とコード生成が、定めた値・借用・外部効果の意味を保つ |

「各機能を個別に研究した例がある」ことと、「この組み合わせが安全」は別である。特に、局所的なクロージャ、domain内にある資源、viewの終了処理、タスクの自動joinを重点的に検証する。

## 6. 実装する場合の順序

この文書では実装を開始せず、後続作業の順序を定める。

1. **値と所有**: 基本型、構造体、関数、move/copy、初期化状態、Result、決定的な終了を実装する。
2. **借用とview**: 場所の重なりと制御フローを検査し、read/inout/initとyieldを実装する。
3. **モードと関数値**: local、明示捕捉、many/mut/once、効果・終了効果を追加する。
4. **domain**: ブランドを持つ型、Arena、Key、CellRefと、領域回収を追加する。
5. **構造化された並行処理**: Send/Sync、scope、join、不変共有、チャネルを追加する。
6. **外部接続**: まず検証用の模擬外部実装でsync_bytesを確かめ、その後にnativeプロバイダーを実装する。

初期の参照実装は、速度よりも規則の可視性を優先したインタープリターでもよい。ABI・タスク・メモリの実際の保証を、ホスト言語の都合で達成したことにしない。最初はモデル上の実装であることを明記する。

## 7. 判定に使う例題

仕様書の適合性表を、将来の検査器の入力へ変換する。受理例だけでなく、近い形の拒否例を対にする。

- 配列の独立した複製と、移譲後の使用。
- 静的に分離したフィールドと、証明されていない動的な添字。
- localな値そのものの返却と、独立したスカラー・copyの返却。
- 同じキーでの複数読み取りと、読み取りが残る間の変更。
- 異なるブランドの取り違え、クロージャ・型引数を通じた持ち出し。
- 所有捕捉を読むクロージャと、呼び出し中に消費するクロージャ。
- 子へ移譲した所有値と、親からの利用、scope外へのTaskの持ち出し。
- init/inoutの通常return・Err・`?`での未初期化状態。
- 外部関数の戻り値の不正と、契約を破る外部書き込みの違い。

ネイティブ実装の段階では、メモリ検査や別名参照モデルを利用した実行検査も行う。ただし、それを全入力の形式証明として扱わない。

## 8. 後続版で検討するもの

| 機能 | 追加前に決めること |
| --- | --- |
| 同一domainの複数セルの同時変更 | 同一セルでない根拠、重なった場合の動作、キーの借用との関係 |
| domain全体の移譲 | すべての到達経路と権限の封じ込め、ブランドの公開方法 |
| セルの個別削除 | 無効なハンドルの表現、世代番号などの検査、投影中の削除禁止 |
| method bundle | 値を返す・その場で変更・消費する実装の対応と選択規則 |
| 非同期・効果ハンドラ | 捕捉した局所状態、再開回数、キャンセルと所有の関係 |
| 一般の外部プロトコル | 状態機械、保持する資源、失敗時の隔離、ABI表現 |
| ユーザー向け証明 | 証拠の言語、検査器、消去できる情報、モデルとの接続 |
| atomic・ロックフリー | メモリ順序、回収、公開APIの証明義務 |
| ユーザー定義の終了処理 | 再入・失敗・終了効果・部分的移譲との整合性 |
