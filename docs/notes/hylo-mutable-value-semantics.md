## 1. Hyloは、どんな言語か

Hyloは、**可変値意味論とジェネリックプログラミングを中心に据えた、安全なシステムプログラミング言語**を目指すプロジェクトである。以前はValという名前でも紹介されていた。[公式サイト](https://hylo-lang.org/)、[Val時代のオブジェクトモデル](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2676r0.pdf)

| 観点 | 概要 |
| --- | --- |
| 主な狙い | 安全性、局所的な理解のしやすさ、低水準の性能を両立する |
| データの中心 | 独立した値。変更も認める |
| 抽象化 | 構造体、trait、ジェネリクス、関数、メソッド、subscriptなど |
| 参照との関係 | 任意に保存・共有する可変参照を通常のモデルの中心に置かず、一時的なアクセスを表す |
| コード生成 | ネイティブコードへコンパイルする。公開処理系はSwiftで実装され、LLVMを使う |
| 開発状況 | 開発中。公式紹介は、まだ一般利用の準備ができていないとしている |

Hyloは純粋関数型言語として設計されているわけではない。変更を用いた命令的な処理と、値を変換する関数型の書き方を組み合わせられる設計である。[言語の公式紹介](https://hylo-lang.org/introduction/)、[関数の説明](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/)、[現在の処理系](https://github.com/hylo-lang/hylo-new)

この言語を理解するには、「何でも参照として共有してから、変更の衝突を抑える」という出発点をいったん離れ、**値を独立に扱い、必要なときだけ一時的なアクセスを許す**という順序で考えるとよい。

## 2. 値意味論と参照意味論を区別する

### 2.1 参照意味論では、別の名前が同じ状態を指せる

次は、共有された可変オブジェクトを扱う言語をイメージした擬似コードである。

```text
a = オブジェクト [1, 2, 3]
b = aへの参照
bの先頭を9にする

aから見ても [9, 2, 3]
bから見ても [9, 2, 3]
```

`a`と`b`は、同じオブジェクトへの別の経路である。`b`を変更する処理を理解する際にも、`a`を通じた観察や変更を考慮しなければならない。

### 2.2 値意味論では、独立した値として扱う

```text
a = 値 [1, 2, 3]
b = aから作った独立した複製
bの先頭を9にする

aは [1, 2, 3] のまま
bは [9, 2, 3]
```

ここで重要なのは、`b`の変更が、`a`の値を背後から変えないことである。物理的にどの記憶領域を使うか、いつバイト列を複製するかとは、ひとまず分けて考える。[MVSの実装戦略に関する研究](https://www.jot.fm/contents/issue_2022_02/article2.html)

### 2.3 「値」は、小さいデータだけを意味しない

整数だけでなく、文字列、配列、木、行列、グラフ全体などにも、独立した値という意味を与えられる。大きな値だから必ず共有可変オブジェクトにしなければならない、という関係はない。

また、値意味論は、値の比較に単に`==`を使うことや、構造体という構文を使うことだけでは決まらない。内部の共有状態を通じて複製元の観測結果が変わるなら、期待した独立性は成立しない。MVSの研究は、こうした独立性をプログラミングの規律として扱う。[Implementation Strategies for Mutable Value Semantics](https://www.jot.fm/issues/issue_2022_02/article2.pdf)

## 3. 可変値意味論の核心

### 3.1 変更を認めつつ、共有された可変状態を制限する

Mutable Value Semanticsは、独立した値について、その全部や一部分をその場で変更できるようにする考え方である。

```text
var image = 独立した画像の値
imageの指定した画素を変更する
imageの一部分だけを塗りつぶす
```

画像全体を毎回、新しい不変の画像へ作り直す必要はない。変更中の画像へ、別の自由な参照経路から干渉できないという条件を守れば、その場での変更と局所的な推論を両立できる。

2021年の研究は、変更を禁止する方向と、自由な参照を複雑な規則で制御する方向に対し、共有を制限して部分的な変更を認める設計を示した。[Native Implementation of Mutable Value Semantics](https://arxiv.org/abs/2106.12678)

### 3.2 「可変」と「参照意味論」は別の性質

| 性質 | 問い |
| --- | --- |
| 可変か不変か | この値を変更できるか |
| 値意味論か参照意味論か | 別の経路を通じた変更が、この値の観察へ影響するか |

可変な値を持ちながら、別の独立した値へは影響を伝えない設計ができる。ここが「可変値意味論」という名前の要点である。

反対に、共有参照を定数の変数へ入れただけでは、参照先の状態まで不変になるとは限らない。Hyloの`let`は、単に変数名への再代入を禁止するだけではなく、その束縛を通じて扱う値の不変性を意図する。[Hyloの束縛](https://hylo-lang.org/docs/user/language-tour/bindings/)

### 3.3 独立性は、現在アクセスできる経路について守る

Hyloでも、値の一部を変更するために、一時的な名前を付けられる。

```hylo
public fun main() {
  var point = (3, 4)
  inout x = &point.0
  &x = 42

  precondition(point.0 == 42)
  precondition(point.1 == 4)
}
```

`x`は、`point.0`の独立したコピーではない。元の値の一部を一時的に投影したものである。そのアクセスが有効な間、重なる経路からの干渉を許さない。

したがって、「値意味論なら、別の名前を付けた操作は必ずコピーになる」という理解も正しくない。**独立した値の複製と、一時的にアクセス経路を切り替えることを区別する**必要がある。[inout束縛の説明](https://hylo-lang.org/docs/user/language-tour/bindings/)

## 4. 値意味論でも、代入が自動コピーになるとは限らない

### 4.1 Hyloでは、コピーは原則として明示する

```hylo
public fun main() {
  var original = (1, 2)
  var independent = original.copy()

  &independent.0 = 9

  precondition(original.0 == 1)
  precondition(independent.0 == 9)
}
```

ここでは、`copy()`により独立した値を作るという意図が明示されている。

一方、`var`の初期化など、所有する値を受け取る操作では、元の束縛を消費する。

```hylo
public fun main() {
  var original = (1, 2)
  var destination = original
  &destination.0 = 9

  // print(original) // 有効にすると、消費済みの値の使用になる
}
```

この二つは、同じ処理ではない。前者は独立した複製を作り、後者は元の値の利用を終えて新しい側へ渡す。[消費する操作と明示的なコピー](https://hylo-lang.org/docs/user/language-tour/bindings/#lifetime)

### 4.2 値意味論とコピー規則は、別々に設計できる

2021年の研究用言語MVSLは、代入でコピーする単純な意味を定め、不要なコピーを最適化するモデルを使う。一方、Hyloの言語ツアーは、コピーを原則として明示し、消費する操作を区別する。

**MVSという意味論の規律と、研究用モデルやHyloが選ぶコピー構文を混同しないことが重要である。**[MVSLの説明](https://arxiv.org/html/2106.12678v1)、[Hyloの束縛と消費](https://hylo-lang.org/docs/user/language-tour/bindings/)

### 4.3 意味上のムーブと、メモリの転送量も別

値を消費して別の場所へ渡すことは、巨大な配列の全要素を物理的に移すことと同義ではない。内部バッファの管理情報だけを渡す、元と同じ領域を利用するなどの実装が考えられる。

ムーブが与えるのは、「元の側は、引き続きその値を使わない」という保証である。実際に何バイト動くかは、値の表現やコンパイラに依存する。

## 5. 四つの受け渡し規約で、関数境界を越える

Hyloは、引数の型に加え、引数をどう扱うかを区別する。

| 規約 | 関数に与えるもの | 呼び出し後 | 主な用途 |
| --- | --- | --- | --- |
| `let` | 変更されない値への一時的な読み取り | 呼び出し側で利用を続けられる | 調査・計算 |
| `inout` | 値を一時的に排他的に変更する権限 | 有効な値が呼び出し側に残る | その場更新 |
| `sink` | 値の所有権 | 元の側では消費済みになる | 保存・返却・所有権の移譲 |
| `set` | 未初期化の格納先 | 初期化された値になる | 初期化 |

この区別はVal時代のオブジェクトモデルでも中心となっている。[The Val Object Model, §3.3](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2676r0.pdf)

### 5.1 letは「毎回コピーして渡す」ではない

```hylo
fun sum(pair: let {Int, Int}) -> Int {
  pair.0 + pair.1
}
```

`let`はデフォルトの受け渡し規約でもある。意味の上では独立した不変値を読むように考えられるが、物理的にコピーを作る必要はない。呼び出しの間、別の経路から引数が変更されないという保証を利用できる。

`let`引数を、所有する結果としてそのまま返すことはできない。独立した結果が必要ならコピーするか、所有権を受け取る`sink`などを選ぶ。[let引数の説明](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#let-parameters)

### 5.2 inoutは、一時的な排他アクセス

```hylo
fun add_to(target: inout Int, by amount: Int) {
  &target += amount
}

public fun main() {
  var score = 10
  add_to(&score, by: 5)
  precondition(score == 15)
}
```

呼び出し側の`&`は、アドレスを自由に取り出す演算子ではなく、変更のためのアクセスを示す印である。

`inout`は、呼び出し中だけ値を預かり、戻るときに有効な値を返すように理解できる。所有権を恒久的に受け取る`sink`とは違う。実装では、内容を移動せず、同じ場所を直接操作できる。[inout引数の説明](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#inout-parameters)

### 5.3 sinkは、呼び出し先へ値を渡し切る

```hylo
fun increased(value: sink Int) -> Int {
  &value += 1
  return value
}
```

呼び出し先は、受け取った値を保持したり、結果として返したりできる。呼び出し側の元の束縛は消費される。[sink引数の説明](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#sink-parameters)

### 5.4 setは、初期化前後の状態を区別する

`set`は、まだ値が入っていない格納先を受け取り、初期化するための規約である。単に既存の値を変更する`inout`とは、入口で満たすべき状態が異なる。[set引数の説明](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#set-parameters)

公式ツアーは、`inout`でも一時的に中身を破棄して再初期化する使い方を説明している。ただし、関数の出口では有効な値へ戻っている必要がある。ここには、単なる読み書きの権限に加え、初期化状態の追跡も関わっている。

## 6. Projectionとsubscript: 値を返さず、一時的なアクセスを渡す

### 6.1 関数で値を返すだけでは困る場面

二つの値のうち小さいほうを選び、呼び出し側でその元の値を変更したいとする。

単に値をコピーして返す関数では、返した値だけが変わり、元の値は変わらない。一方、自由な可変参照を返す方法では、その参照の生存期間や共有関係を扱う必要がある。

Hyloは、このような場面に**projection（投影）**と**subscript**を使う。Subscriptは添字アクセスだけを意味するものではなく、対象やその一部への一時的なアクセスを提供する抽象化である。[subscriptの公式説明](https://hylo-lang.org/docs/user/language-tour/subscripts/)

### 6.2 小さいほうを、その場で変更する

次は、公式トップページの例と同じ構文による説明例である。

```hylo
subscript smaller(a: inout Int, b: inout Int) inout -> Int {
  if a < b { yield &a } else { yield &b }
}

public fun main() {
  var (x, y) = (4, 2)
  inout selected = &smaller[&x, &y]
  &selected += 10

  precondition(x == 4)
  precondition(y == 12)
}
```

`selected`は、小さい値の複製ではなく、選ばれた`y`への投影を表す。その投影の利用が終わった後で、元の変数の値を確認する。

`&`が現れても、プログラムが生ポインタを自由に取得しているわけではない。また、`smaller`を関数と同じような、任意に保存できる参照値を返すものと考えないことが重要である。[公式トップページの投影の例](https://hylo-lang.org/)

### 6.3 yieldは、呼び出し側へ制御を一時的に渡す

```text
subscriptを開始する
    ↓
対象を選び、yieldで投影を提供する
    ↓
呼び出し側が、投影した値を読む・変更する
    ↓
投影の利用を終える
    ↓
subscriptの残りの処理へ戻り、終了する
```

この形により、アクセスが続く範囲を囲める。Subscriptの処理は、値を返して完全に終了する普通の関数呼び出しとは異なる。

なお、`sink`版のsubscriptには、投影ではなく値を消費して返す場合もある。「すべてのsubscriptが、常に同じ投影だけを行う」と一般化しない。[subscriptの動作と各variant](https://hylo-lang.org/docs/user/language-tour/subscripts/)

### 6.4 内部を直接操作できても、抽象化は保てる

行列の一行、辞書の要素、スタックの先頭などを投影すれば、呼び出し側はその部分を直接変更できる。コレクション全体をコピーして、変更後に書き戻す必要がない。

同時に、実装側はアクセスの前後に必要な処理を置ける。Projectionは、「自由な参照を外へ放り出す」ことと、「常に全体を値で作り直す」ことの間に、効率的な抽象化の方法を作る。[Valの投影と制御の反転](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2676r0.pdf)

## 7. ライフタイム注釈を省ける理由と、借用検査

### 7.1 別経路からの干渉を、呼び出しの条件で拒否する

5節の`add_to`に対し、次のように同じ値を渡すことを考える。

```hylo
var score = 10
add_to(&score, by: score) // 拒否を意図した例: 変更する経路と読む経路が重なる
```

関数の中では、`target`を変更しても`amount`は変化しないという前提で処理を書ける必要がある。同じ値を、独立した引数のように二つの経路へ渡すと、この前提が壊れる。

独立した値として使いたいなら、事前にコピーする。

```hylo
var score = 10
let increment = score.copy()
add_to(&score, by: increment)
```

Hyloの関数境界での排他性は、こうした潜在的な重なりを制限する。[重なるinout引数の説明](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#inout-parameters)

### 7.2 ライフタイム注釈がなくても、生存期間の解析は必要

Hyloの設計は、利用者がRustのようなライフタイム引数を付け、任意の参照関係を型へ記述することを中心にしていない。

これは、寿命や借用の問題をコンパイラが考えなくてよいという意味ではない。2023年の「Borrow checking Hylo」は、中間表現にある寿命に関する情報を抽象解釈で処理し、安全性を検査する方式を説明している。[Borrow checking Hylo, IWACO 2023](https://2023.splashcon.org/details/iwaco-2023-papers/5/Borrow-checking-Hylo)

### 7.3 第一級の参照と、投影に名前を付けることは違う

通常の参照型を、変数・フィールド・戻り値などへ自由に保存するモデルでは、長く残る参照どうしの関係を管理する必要がある。

MVSの研究用モデルは、そうした第一級の参照を制限する。一方、Hyloで`inout selected`のように投影へ名前を付けることは、制約付きの一時的なアクセス経路を使うことであり、自由に保存・持ち出せる参照値を作ることとは異なる。[MVSの研究用モデル](https://arxiv.org/abs/2106.12678)、[Hyloの投影](https://hylo-lang.org/docs/user/language-tour/bindings/)

Hyloの内部実装や`unsafe`な機能まで含めて、ポインタが一切存在しないと説明するのも適切ではない。ここで扱っているのは、通常の安全なコードを理解するための利用者向けモデルである。

### 7.4 局所的な推論は、何を楽にするのか

ある関数の`inout`引数を変更しても、別の独立した引数が勝手に変わらない。不変な引数は、コールバックを呼んだ前後でも、別経路から突然変更されない。

この条件があると、人間は関数本体と明示された引数を中心に理解できる。コンパイラも、隠れた別名参照から変更されるかもしれないという保守的な想定を減らせる。これがMVSの重要な狙いである。[MVSの局所的な推論と最適化](https://www.jot.fm/issues/issue_2022_02/article2.pdf)

## 8. クロージャとジェネリックプログラミング

### 8.1 クロージャも、状態を持つ値として扱う

クロージャは、引数に見えない状態を捕捉できる。そのため、値の独立性を保つには、捕捉にも規律が必要になる。

Hyloのツアーは、読み取りの`let`、変更の`inout`、所有する値を取り込む`sink`という捕捉を区別する。クロージャ自身が状態を持ち、呼び出すたびにその状態を変える例では、クロージャへの呼び出しも変更として扱う。[クロージャの捕捉](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#closure-captures)

```text
counter = 「自分の内部に整数iを所有する」クロージャ

counterを変更する呼び出し → iを進め、次の数を返す
counterの値を独立に複製   → 複製側の状態は独立して進む
```

この擬似コードは、コピー可能な状態を持つクロージャの意味を説明するものである。すべてのクロージャが複製可能であることや、すべての捕捉が自動的にコピーされることは意味しない。

### 8.2 一つの操作に、複数の利用形態がある

たとえば、ベクトルへオフセットを加えるという同じ処理にも、次の形がある。

| 利用形態 | 何をするか |
| --- | --- |
| `let`側 | 元の値を保ち、新しい値を作る |
| `inout`側 | 元の値をその場で変更する |
| `sink`側 | 元の値を消費し、変更後の値を返す |

Hyloのmethod bundleは、こうした意味上の関係を持つ実装を、一つの操作名にまとめる機能である。呼び出しの文脈や最後の使用かどうかなどから、適切なvariantを選び、場合によっては実装を合成する。[method bundleの説明](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#method-bundles)、[Method Bundles, 2024](https://graphsearch.epfl.ch/en/publication/2e71e1a6-3406-4688-9a67-4967012a002c)

### 8.3 ジェネリクスと、受け渡し規約を組み合わせる

Traitは、型に必要な操作を要求する仕組みである。ジェネリックなアルゴリズムは、具体的な型を固定せず、その要件に従って書く。

そこで、読み取るだけなら不要なコピーを要求せず、変更するなら`inout`、所有するなら`sink`、複製が必要な箇所ではコピーの要件を課す、といった使い分けが重要になる。[公式サイトのtraitとジェネリクスの例](https://hylo-lang.org/)

可変値意味論は、すべての型について自由な複製を要求する考え方ではない。資源を表す値についても、所有や複製の能力を型・APIの要件として区別する必要がある。[Hyloの資源管理traitに関する研究](https://repository.tudelft.nl/file/File_a1dfd2ef-db9b-42c3-a891-31f68e2f3ae9?preview=1)

## 9. 実装では、どう効率を保つのか

### 9.1 意味上の独立性と、物理的な配置を分ける

「独立した値」と聞くと、すべての代入や関数呼び出しで大きなデータを深くコピーするように感じられる。しかし、意味を保てる範囲で、その物理的なコピーを避けられる。

代表的な手段は、次のとおりである。

| 手段 | 利用する情報 |
| --- | --- |
| 値のインライン配置・スタック配置 | 値の大きさと生存範囲 |
| `let` / `inout`による一時的なアクセス | 呼び出し中の不変性・排他性 |
| ムーブ | 元の値の利用が終わること |
| Copy-on-Write | 記憶領域が共有されているか |
| 不要なコピー・変更の除去 | その結果が他から観察されないこと |

これらはMVSの研究が検討してきた実装戦略であり、Hyloの全型が同じ方法で実装されるという意味ではない。[2021年の実装研究](https://arxiv.org/html/2106.12678v1)、[2022年の拡張研究](https://www.jot.fm/issues/issue_2022_02/article2.pdf)

### 9.2 Copy-on-Writeなら、内部で共有しても独立性を保てる

```text
意味の上では:
  a = 独立した配列の値
  b = aの独立した複製

物理的な記憶領域は、変更前には共有できる:
  a ──→ バッファ [1, 2, 3] ←── b

bの変更が必要になったら、必要な複製を作る:
  a ──→ バッファ [1, 2, 3]
  b ──→ バッファ [9, 2, 3]
```

「共有を制限するMVSなのに、内部では共有するのか」という疑問に対しては、**利用者から観察できる可変状態の共有と、実装上のバッファ共有は別である**と答えられる。

変更時に必要な複製を行えば、片方の変更がもう片方へ伝わらない。2022年の研究は、動的な大きさを持つコンテナについて、こうした戦略を検討している。[Copy-on-Writeを含む実装戦略](https://www.jot.fm/contents/issue_2022_02/article2.html)

### 9.3 CoW自体には費用がある

参照カウント、一意性の検査、共有時のバッファ複製などが必要になる。共有された大きな配列へ一度書き込むだけでも、大きなコピーが発生する場合がある。

逆に、領域が一意であることがわかるなら、複製せずその場で更新できる。MVS、明示的なコピー、CoWは互いに同義ではなく、意味・構文・実装の別々の層に属する。

### 9.4 回収方式まで、一つに決まるわけではない

MVSの研究実装は、値の生存範囲に基づく破棄や、CoW用の参照カウントなどを組み合わせる。したがって、MVSを「どんな実行時メモリ管理も要らない仕組み」と説明することはできない。

また、利用者向けモデルが値中心であることから、現在のHylo処理系の全割り当て、破棄の時点、FFIの挙動まで自動的に導けるわけではない。本メモでは、研究モデルの実装方法を、そのまま現行処理系全体の保証とは扱わない。

## 10. 所有関係が木でも、グラフは表現できる

### 10.1 「所有する」と「関連がある」を分ける

一つの値が、その部分となる値を所有する形をたどると、木のような構造になる。ここから、循環するグラフや双方向リストを表せないのではないか、という疑問が生じる。

解決の一つは、**グラフのノードを一か所で所有し、辺はノードの識別子で表す**ことである。

```text
Graphという値
  nodes:
    A → ノードAのデータ
    B → ノードBのデータ
  links:
    A → [B]
    B → [A]
```

論理的なグラフには循環があるが、辺は識別子という値であり、ノードの中身を自由に変更する別の参照権限ではない。ノードを読む・変更するには、`Graph`を通す。

### 10.2 双方向リストにも、同じ発想を使える

ノードを配列などでまとめて所有し、前後のノードを添字で示す方法がある。ポインタを直接貼る代わりに、コンテナと識別子を使う。

2025年の「Who Owns the Contents of a Doubly-Linked List?」は、Webグラフと双方向リストについて、この種の値中心の表現を研究している。**例と測定はSwiftによるもので、Hyloコンパイラの性能測定ではない。**[2025年の原論文](https://drops.dagstuhl.de/storage/01oasics/oasics-vol134-programming2025/OASIcs.Programming.2025.25/OASIcs.Programming.2025.25.pdf)

### 10.3 できることは変わらなくても、APIの重心は変わる

参照を各ノードへ配るAPIから、グラフを受け取り識別子で操作するAPIへ設計が変わる。これにより、不変条件をコンテナ側へまとめ、データの配置を改善しやすくなる。

一方で、識別子が有効か、別のグラフへ取り違えて使っていないか、削除後に再利用された場所を誤認しないかなどは、別に設計しなければならない。

世代番号やブランドを付ける方法も考えられるが、これは本メモからの追加の検討案であり、Hyloがすべての識別子へ自動でその保証を付けるという意味ではない。

## 11. 並行処理と保証の範囲

### 11.1 独立した値は、並行に扱いやすい

二つの処理が独立した値を扱うなら、片方の変更が、もう片方の値へ背後から伝わることを考えずに済む。所有する値を別の処理へ渡す、同時に読む間は変更を禁じる、といった規律も組み合わせられる。

この性質は、データ競合を防ぐ設計の土台になる。ただし、**可変値意味論という言葉だけで、並行実行の仕組みや、その処理系の安全性が完成するわけではない**。どの値を渡せるか、アクセスの期間をどう区切るか、実行時の共有資源をどう扱うかも必要になる。[Hyloの安全性の設計目標](https://hylo-lang.org/introduction/)

### 11.2 Hyloの並行処理は、現在の計画として読む

公式のConcurrencyページには、方式はまだ設計中であり、記述は現在の計画であると明記されている。

そこでは、構造化された並行処理、通常の関数による抽象化、`async`などで関数を色分けしない設計などを検討している。しかし、掲載された`spawn`や`await`の例を、そのまま現在のコンパイラで利用できる安定機能とは扱えない。[並行処理の計画と注意書き](https://hylo-lang.org/docs/user/language-tour/concurrency/)

### 11.3 値の独立性から、すべての副作用は消えない

外部ファイル、ネットワーク、画面への出力などは、値を独立に持つだけでは隔離されない。二つの値が別々でも、同じ外部資源を操作する可能性はある。独立した値の変更と、外部世界への効果は別に考える必要がある。

同様に、データ競合を防げても、処理順序の誤り、デッドロック、論理的な不変条件の違反まで一括して解決するわけではない。Hyloの安全な通常コードについての設計目標と、`unsafe`な操作や他言語との境界の責任も区別する。[通常コードとunsafeの位置づけ](https://hylo-lang.org/introduction/)

## 13. Rust・GhostCell・OxCamlなどとの比較

### 13.1 Rustも、値と一時的な借用を扱う

Rustにも、値の所有、ムーブ、明示的な複製、排他的な変更アクセスがある。Hyloを「値意味論の言語」、Rustを「値意味論を持たない言語」と分けるのは適切ではない。

比較すべきなのは、**参照をどこまで通常のデータとして組み立てられるか、その関係をAPIにどう表すか**である。

Rustでは、参照を構造体やコレクションの要素として扱い、その生存関係をライフタイムで記述できる。Hyloは、値の所有を基本にし、関数引数やprojectionの一時的なアクセスへ制限を設けることで、利用者にライフタイム注釈を要求しない方向を取る。[Hyloの公式比較](https://hylo-lang.org/introduction/)、[所有権と借用の基礎](ownership-and-beyond.md)

したがって、Hyloの「ライフタイム注釈が不要」は、Rustのあらゆる参照を、そのまま同じ形で書けるという約束ではない。データ表現やAPIの組み立て方にも選択を伴う。

### 13.2 GhostCellとは、共有を扱う出発点が違う

[GhostCell](ghostcell.md)は、Rustで複数の参照を持つデータ構造に対し、ノードとは別のトークンで読み書きの権限を管理する。参照関係の自由度と変更の排他性を分ける発想である。

一方、HyloのMVSでは、まず独立した値を基本にし、必要なアクセスを一時的に投影する。グラフなら、コンテナが全体を所有し、辺を識別子で示す形も自然な候補になる。

どちらも「データへ到達できること」と「今変更してよいこと」の区別を考えるうえで参考になる。ただし、GhostCellのブランド付きトークンが、そのままHyloの仕組みなのではない。この対応は、両者の設計を比較するための考察である。

### 13.3 OxCamlは、GCを持つ言語に使用上の規律を加える

[OxCamlのモード](oxcaml-modes.md)は、値の生存範囲、一意性、使用回数、並行処理との関係などを複数の軸で扱う。既存のOCamlの型やGCを基礎に、より詳しい使用条件を追跡する方向である。

Hyloは、値中心のオブジェクトモデルとアクセス規約を言語の基礎に据える。OxCamlの各モード軸と、Hyloの`let`・`inout`・`sink`・`set`には関心の重なりがあるが、一対一に対応するものではない。

| 方式 | 主にどう問題を整理するか | APIや表現で考えること |
| --- | --- | --- |
| Hylo | 独立した値と、一時的なアクセスを基礎にする | コピー・消費・投影の境界。関連を持つデータの所有単位 |
| Rustの所有権・借用 | 所有と参照の生存関係、共有・排他の規則を検査する | 借用の関係を持つAPI、参照を含むデータ構造 |
| GhostCell | データの参照関係から、読み書きの権限を分離する | ブランドとトークンの範囲、複数ノードの操作 |
| OxCamlのモード | 型に加え、値の使い方の複数の性質を追跡する | 各モードの制約、推論、既存コードとの境界 |

これは設計上の重点の比較であり、実行速度や表現力の順位ではない。

### 13.4 Swiftの値型との関係

Swiftの構造体や配列は、可変な値を扱う身近な例になる。MVSの実装研究も、Swiftを重要な比較対象にしている。

ただし、Swift全体には参照型もある。Hyloが値中心の規律を言語全体の基礎として目指すことと、Swiftで値型を選んで使うことは区別する。[Swiftとの関係を含むMVSの研究](https://www.jot.fm/issues/issue_2022_02/article2.pdf)

## 14. このリポジトリの言語設計への示唆

以下は、調査資料から導いた検討案であり、Hyloの仕様や、このリポジトリでの採用決定ではない。

### 14.1 値の独立性、複製、変更を別々に決める

小さな言語を設計するときには、次の問いを分けると整理しやすい。

1. 二つの値の変更は、互いに独立しているか。
2. 代入や引数の受け渡しは、複製するのか、消費するのか、一時的にアクセスするのか。
3. 値の一部分を変更するとき、どの経路を一時的に使えなくするか。
4. 複製できない資源を、どう表すか。
5. 効率化のための物理的な共有を、どこまで利用者から隠せるか。

「値意味論を採る」と決めただけでは、これらは埋まらない。Hyloと初期のMVSLでコピー規則が異なることは、その具体例になる。

### 14.2 最小構成から試すなら、関数境界を先に決める

最初の実験では、独立した値、明示的な複製、消費する受け渡し、一時的な変更アクセスを扱い、参照を自由に保存する機能の必要性を別に検討する構成が考えられる。

その上で、コレクションの要素などをコピーせず変更する必要が出たら、projectionのような機構を加える。ここでは、アクセス中に元の値のどの部分を禁止するか、制御が戻ったときに何が初期化済みであるべきかが設計の中心になる。

### 14.3 小さな例で、境界を確かめる

| 確認する例 | はっきりさせたい規則 |
| --- | --- |
| 配列を複製して片方だけ変更する | 値の独立性と、コピーの費用 |
| 値を渡した後で元の変数を使う | 消費と、再初期化の規則 |
| 同じ値を、変更用と読み取り用の両方へ渡す | 重なるアクセスの扱い |
| 配列の異なる要素を同時に変更する | 静的に証明できる範囲と、実行時検査・APIによる分割の必要性 |
| コレクションの要素を返す・投影する | コピーと一時的なアクセスの違い |
| グラフのノードを削除した後に識別子を使う | 借用の安全性とは別の、識別子の有効性 |

局所的に理解しやすいモデルを目指す場合にも、何を簡単にする代わりに、どの表現をAPI側へ移すかを具体例で評価する必要がある。

- [Who Owns the Contents of a Doubly-Linked List?, 2025](https://drops.dagstuhl.de/storage/01oasics/oasics-vol134-programming2025/OASIcs.Programming.2025.25/OASIcs.Programming.2025.25.pdf): グラフや双方向リストを値として設計する具体例。

### 15.3 今回、確認したことと残したこと

公式サイト、言語ツアー、研究論文、公開処理系のREADMEを照合し、意味論の説明と開発状況を整理した。研究用言語MVSLのコピー規則、現在公開されているHyloの説明、Swiftを使ったデータ構造の研究を区別した。

Hyloコンパイラのビルド、コード例のコンパイル・実行、性能測定、処理系全体の安全性の検証は行っていない。とくに開発中の構文、最適化の実装状況、並行処理の計画については、概念を理解する資料として扱い、実装済みの保証とは分けている。
