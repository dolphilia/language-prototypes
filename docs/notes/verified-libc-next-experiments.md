# 検証済みlibcの試作から、何を次に確かめるか

[メモの一覧](README.md) · [既存の調査](verified-primitives-and-proof-carrying-assembly.md) · [プロトタイプ](../../prototypes/verified-libc-minimal/README.md) · [完了監査](../../prototypes/verified-libc-minimal/reports/audit.md)

調査・考察日: **2026-11-08**

具体化した計画: [検証済みlibcの発展 — 実装・検証計画](../plans/verified-libc-evolution/README.md)。M1の証明合成と任意長コピー、M2の呼び出し元・重複・リンク、M3のモデル・資源・探索へ分けた。提案後の[実施記録](../../prototypes/verified-libc-evolution/reports/progress.md)を別に置いている。以下は提案時点の整理である。

**次の版では、同じAArch64と同じ2関数を土台に、証明済み部品の合成と任意長の8バイトループを確かめることを勧める。** その後、呼び出し側の権限・寿命、重複コピー、リンク、モデルと実機の対応へ進む。各拡張では、何を仮定から証明へ移したか、代わりに何を信頼するようになったかを記録する。

以下は**発展方向と実験の提案**である。今回、プロトタイプのコード・契約・測定値は変更しておらず、ここに書いた拡張を実装・検証したわけではない。既存の実績、外部の前例、本メモの仮説を区別する。

## 1. 今回分かったことと、まだ分かっていないこと

[完了監査](../../prototypes/verified-libc-minimal/reports/audit.md)と実装から、出発点を次のように整理できる。

| 今回確認したこと | そこからは、まだ言えないこと |
| --- | --- |
| 2関数の基本版とコピーの最適化版について、実際の命令列の機能・終了・保存・アクセスを証明した | 呼び出し元が毎回、必要なメモリ権限・寿命・非重複を満たしている |
| マクロの命令列と小さな定理を用意した | 任意の部品を合成するだけで、親の証明を安く作れる |
| 最適化版に埋め込んだ基本版の定理を再利用した | ループ、分岐、レジスタ変更、関数間呼び出しを一般的に合成できる |
| M1 Proの整列済み8バイトコピーで高速化した | 任意長・未整列・別の機器・大きな作業領域でも高速である |
| 選択した2関数の本体は92バイトで、実行時の証明処理がない | 抽象化、探索、ラッパーを増やしても速度・容量を維持できる |
| Mach-Oとリンク後の全命令バイトを照合した | 抽出処理・リンカ・OSローダー全体が形式検証された |
| 追加公理を拒否し、期待する閉じた定理を確認した | HOL Light・OCaml・ISAモデル・実機との対応まで信頼が不要になった |

特に、HOL Lightの**閉じた定理**も、`PならばCはQを満たす`という条件付きの命題になり得る。定理の未処理の仮定がないことと、利用条件や外部への信頼がないことは違う。

現在の[生成器](../../prototypes/verified-libc-minimal/generator/main.ml)は命令文字列と期待語列を持つ小さな構造で、[マクロ](../../prototypes/verified-libc-minimal/proofs/macros.ml)はコード定義と定理の組を持つ。ただし、基本版のループ本体では命令を改めてシミュレーションしている。ここが、証明を再利用する構築環境へ進む際の、具体的な検証対象になる。

同様の境界はs2n-bignum自身も整理している。形式仕様と要求、ISAモデルと実機、呼び出し条件と利用者のコードには、それぞれ別の隔たりがある。[s2n-bignumの健全性の整理](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md)

## 2. 「仮定の検証」を三つに分ける

| 種類 | 例 | 次に行うこと | 得られる結論 |
| --- | --- | --- | --- |
| 設計上の仮説 | 証明付きマクロなら開発負担を減らせる | 同じ処理を直接証明する版と合成する版で比較 | 観測した規模・変更における開発上の有効性 |
| 論理上の事前条件 | 出力が有効で、入力と重複しない | 呼び出し側の型・領域・制御から導出する | より大きなプログラムについての条件付き定理 |
| 外部との対応についての信頼 | ISAモデルが対象CPUを表す | 別の実装や実機との照合、モデルの精密化 | 対応への追加の根拠。物理世界との隔たりすべての解消ではない |

「仮定をなくす」を一つの成功条件にすると、外部の条件を単に別の場所へ移しただけでも成功に見えてしまう。以降では、**前提を証明で導出する・実行時に検査する・別の主体へ委ねる・明示して残す**のどれを行ったかを区別する。

## 3. 発展の全体像

| 実験 | 確かめる仮説 | 最小の拡張 | 期待する軽減と、新たな負担 |
| --- | --- | --- | --- |
| E0: 根拠の区別 | 検査の失敗を、誤実装の反証と区別できる | 具体的な反例と正しい変形を試験へ加える | 誤った成功・失敗の解釈を減らす。反例の再現処理が必要 |
| E1: 部品の合成 | 証明とコードを一緒に抽象化できる | Copy8を2回合成する16バイトの部品 | 親の命令単位の証明を減らす。フレーム・配置・レジスタの接続が必要 |
| E2: 任意長の高速化 | 同じ契約のまま性能の適用範囲を広げられる | 8バイトの反復と0〜7バイトの端数 | 長さ8だけの特殊化を越える。算術・境界・性能選択が複雑になる |
| E3: 呼び出し側の検証 | ライブラリの前提を利用者のコードから導ける | 同じ所有領域を分割してコピーする小さな呼び出し元 | 外部契約を毎回手で確認する負担を減らす。権限の発行元とFFIの意味が問題になる |
| E4: 重複の扱い | 非重複の仮定をアルゴリズムで取り除ける | バイトループの`memmove` | 適用範囲が広がる。開始時の入力と更新順序を追う必要がある |
| E5: 関数間と最終成果物 | 関数を分けても証明をつなげられる | 一つの直接呼び出しと限定した再配置 | ライブラリとしての構造化が可能になる。復帰先・ABI・配置の証明が増える |
| E6: モデルと検査器 | 一つのモデル・実行環境への依存を減らせる | 使用命令だけの差分検査と、証明の別検査の調査 | 対応への根拠が増える。独立した実装の維持と意味の整合が必要 |
| E7: 資源と最適化 | 資源の保証と探索を安全に組み合わせられる | ステップ数の定理と少数の実装候補の探索 | 最適化を証明担当者だけに依存させずに済む。探索費用と測定の偏りが増える |

これらを一度に進める必要はない。E0で根拠の扱いを整え、E1・E2で小さな構築環境の有効性を確かめ、E3以降で信頼の境界を広げる順序がよい。

## 4. E0 — 検査の拒否と、反例を区別する

現在の[意味を壊す試験](../../prototypes/verified-libc-minimal/tools/negative_proofs.py)は、実物と期待命令を一緒に変更し、元の証明タクティックが成功しないことを確かめている。これはバイトの固定だけではない有用な検査だが、**タクティックの失敗だけで、命題が偽だとは証明できない。** 正しい別の実装にも、別の証明が必要になることがある。

次は、次の三つを別々に記録する。

1. **証明済み:** 期待する契約の定理を検査できた。
2. **反例あり:** 契約を満たす具体的な初期状態から、結果・アクセス・保存状態の違反を再現できた。
3. **未解決:** 証明も反例も得られていない。タイムアウト、未対応命令、証明手順の不足もここへ含める。

受理するのは1だけでよい。一方、2と3は研究上の結論が違う。

最小の追加実験は以下である。

- 戻り値の破壊は非ゼロの`dst`とゼロ長で、読み過ぎ・書き過ぎは1バイトの領域で、具体的な違反を再現する。可能なら、そのモデル内の有限実行の違反自体もHOLで検査する。
- 非終了の例には、復帰命令をその位置への自己分岐に置き換え、戻り先とPCが異なる条件で、戻り先に到達しないことを示す。ランキング式の証明失敗だけを非終了の証拠にはしない。
- 同じレジスタをゼロにする別の命令など、意味を保つ変形も正例へ加える。旧証明が失敗しても、新しい証明で元の契約を満たせるかを調べる。
- 反例の検査では、初期状態が**事前条件を満たすこと**も確認する。契約外の呼び出しが壊れたことを、実装の誤りと数えない。

通過条件は、すべての既存の破壊例について「どの根拠で拒否したか」を報告でき、正しい変形の証明不足を誤実装として数えないことである。

## 5. E1 — マクロを、定理を合成できる部品にする

ここは当初の「公理や定理のような部品から、高度な操作を構築する」という構想へ最も直接につながる。

### 5.1 最初の一例

まず、次の16バイトの処理だけを対象にする。構文は設計上の説明であり、新言語の仕様ではない。

```text
copy16 = sequence(
    Copy8(dst + 0, src + 0),
    Copy8(dst + 8, src + 8))
```

親は16バイト分の読書き権限、非重複、整列を要求する。二つの部品へ必要な範囲を渡し、最終状態・保存状態・イベント列・終了を合成する。各部品内部のロード／ストアを、親の証明で再実行する必要があるかを確かめる。

現在のマクロのオブジェクトには末尾の`ret`も含まれ、部品の定理はその手前までを扱う。合成用の版では、命令本体と関数の復帰処理を明確に分け、コードの部分列とPCの配置を扱う補題が必要になる。既存の`thm`二つの組だけで、これが自動的に得られるわけではない。

### 5.2 部品が保持するもの

| 情報 | 必要な理由 |
| --- | --- |
| コードの定義と、そのコードについての定理 | 同名の別コードや、違う命題の定理との取り違えを防ぐ |
| 事前・事後条件 | 前の部品の結果から、次の部品の条件を導く |
| 読み取り・書き込み範囲と保存条件 | 他の領域・元の入力・呼び出し元の状態を保つ |
| レジスタとフラグの変更 | 一時レジスタや条件フラグを、後の部品が誤用しない |
| PC・配置・分岐先 | インライン展開と実際の命令位置を対応づける |
| アクセスイベントと終了 | 最終値だけでなく、途中の安全性と有限実行も合成する |
| 残る前提 | 子の前提の未解決部分を、親の前提から落とさない |

最初は固定レジスタのままでよい。次に一つだけ一時レジスタを差し替え、その置換が引数・戻り値・保存レジスタを壊さないことを示す。パーサーや汎用のレジスタ割り当ては後に回す。

OCamlの抽象型で誤った組み合わせを作りにくくすることは有用だが、それを正しさの新しい公理にはしない。合成結果はHOLの定理として導出し、実物の命令列とも照合する。

**通過条件:** 直接記述した版と合成した版の命令本体が全バイト一致し、証明データ・余分な呼び出し・検査が実行コードに出ない。さらに16・32バイト等の少数の例で、親の命令単位の証明を置き換えられることを確認する。レジスタ衝突や不足した書き込み範囲は拒否する。

**負担の評価:** 証明の行数だけでなく、契約や部品を一か所変更した際の修正箇所、証明時間、手動のヒント数を記録する。ロード時間と部品の再証明、親の合成時間を分ける。現在の全検査約489秒を、そのまま合成の速さと比較しない。

Valeには、事前・事後条件と変更範囲を持つ手続き、マクロ、生成時のインライン展開がある。Jasminも低水準の制御と構造化を組み合わせる。これらは構成の参考になるが、その実装を導入すれば現在のHOL・Mach-Oの接続も自動的に完成する、という意味ではない。[Valeの手続きとマクロ](https://project-everest.github.io/vale/programs.html)、[Jasminの公式説明](https://jasmin-lang.readthedocs.io/en/stable/)

## 6. E2 — 同じ公開契約で、任意長の8バイトループへ進む

現在の最適化は`n == 8`の一例である。次の実験は、**両アドレスが8バイト整列している場合に8バイトずつ反復し、端数だけを1バイトで処理するコピー**に絞る。未整列なら基本版へ進む。公開契約へ新しい整列や余分な読み取り許可を加えない。

数学的には`n = 8q + r`、`0 <= r < 8`に分ける。実装では残量を使い、`remaining >= 8`を確かめてからロード／ストアし、残量を減らす。機械語で`i + 8`を先に計算する場合は、その計算自体の折り返しも別途証明する。

主な証明事項は次の通り。

- 先頭の処理済み領域は開始時の入力と一致し、まだ必要な入力は保存される。
- 各8バイトの範囲が有効領域へ収まり、最終ブロックでも読み過ぎ・書き過ぎがない。
- アドレスとカウンタの計算が折り返さず、残量が減少する。
- 端数0〜7、ゼロ長、未整列への分岐を含め、同じ公開契約を満たす。

両アドレスを同じだけ進めても、元の整列のずれが違えば両方を同時には8バイト整列できない。したがって「数バイト処理すればいつでも両方が整列する」とは仮定しない。未整列の8バイトアクセスやSIMDは、この実験の後で別に評価する。

**通過条件:** 現在のバイト仕様に対する機能・終了・保存・アクセスの証明が通り、長さ7/8/9、15/16/17等の境界破壊を拒否する。証明に成功しても速度が改善しなければ、性能上は未達と記録する。

**比較する版:** 基本版、現在の長さ8専用版、新しい8バイトループ版、システムlibcを分けて保存する。新しい版が全条件で勝つとは想定しない。長さ8専用版を残すかも、サイズ・分岐費用・測定結果で判断する。

同じ方法で`memset`へも適用できるが、先にコピー一つで部品合成と端数の方法を固める。

## 7. E3 — 呼び出し条件を、利用者のコードから導く

現在は「正しい領域を渡したなら安全」を示している。次は、**その領域を渡すまでの小さなプログラム**を対象にする。

最初の例には、一つの既知の所有領域を二つの非重複な部分領域へ分割し、片方からもう片方へコピーする処理が向く。領域の生成・分割・借用・返却を追い、長さ・寿命・読書き権限・非重複から機械語の入口条件を導く。アロケータ全体を最初から証明する必要はなく、入口の所有領域の有効性は明示して残す。

設計のイメージは、`ReadRegion(src,n)`と`WriteRegion(dst,n)`の権限を引数として受け取ることである。権限を証明専用の値にできれば、機械語の引数は既存のポインタと長さのままでよい。ただし、その消去とABIへの対応も確認対象になる。

**ポインタと長さを構造体へ入れるだけでは、その権限は成立しない。** 権限の発行元、解放後の失効、別経路の書き込み、外部コードへの受け渡しを扱う必要がある。`n <= capacity`の実行時検査だけでは、解放済みポインタやデータ競合は分からない。

Rustの`&[u8]`と`&mut [u8]`を入口にしたラッパーも、実用的な比較対象になる。まず初期化済みのバイトだけに限定し、型付きの任意の`T`や未初期化値は広げない。Rustのコピー操作にも、有効性・整列・非重複等の条件がある。[Rustの`copy_nonoverlapping`の条件](https://doc.rust-lang.org/std/ptr/fn.copy_nonoverlapping.html)

ただし、ラッパーをコンパイルして試験した段階と、Rustの意味・ポインタの由来・FFI・機械語の契約の対応まで証明した段階は分ける。AArch64の平坦なバイトメモリ上の定理だけから、安全なRust APIの健全性まで導いたことにはしない。

**通過条件:** 実行可能な小さな呼び出し元について、ライブラリの入口条件が導かれる。権限の重複、範囲を越えた分割、寿命外の再利用は拒否する。ラッパー自身の長さ検査・呼び出し・容量の費用も、本体とは別に測る。

## 8. E4 — `memmove`で非重複の仮定を取り除く

新しい関数を一つ加えるなら、次の候補は`memmove`である。新しい命令を大量に加えずに、既存の重要な前提を一つ取り除く実験になる。

まずバイト単位の前向き・後ろ向きループだけにする。結果の仕様は、重複の有無にかかわらず「**呼び出し開始時点の入力**の`n`バイトが出力へ移る」とする。

重複時には、出力への書き込みが入力領域も変更する。したがって、コピー中ずっと入力全体が不変という現在の不変条件は再利用できない。更新順序に応じて、これから読む部分がまだ開始時の値であることを示す必要がある。同一アドレス、ずれ1、`n-1`、隣接、ゼロ長を含める。

アドレス比較は今回の非折り返しを持つ機械語の契約で扱う。将来C等の高水準言語で実装する場合、その言語で無関係な領域のポインタを同じ方法で比較できるかを、別に確かめる。

**通過条件:** 非重複を要求しない独立した仕様を証明し、常に前向きに処理する破壊例などについて重複時の反例を得る。他の有効性・寿命・排他的な書き込みまで不要になったとは扱わない。

次の関数候補としては、読み取りだけの`memcmp`、容量を渡す有界の文字列走査がある。生の`strlen`は、終端が有効領域内に存在する等の条件なしに、安全な終了を保証できる対象ではない。ここは言語の型やAPIが何の情報を要求すべきかを考える実験になる。

## 9. E5 — 関数分割、再配置、証明付き成果物

現状は1関数1オブジェクト、外部呼び出しとコードの再配置なしである。この限定を一つずつ外す。

最初は、同じ実行ファイルへ静的に組み込む補助関数一つへの直接呼び出しだけを扱う。対象のPC相対分岐の再配置を限定し、スタブ・動的解決・関数の差し替えは後に回す。呼び出しを行う側は、元の復帰先を保存する必要もある。現在の葉関数の資源契約を、そのまま親にも適用しない。

二つの進め方を比較できる。

| 方針 | 証明する接続 | 残る負担 |
| --- | --- | --- |
| リンク後の命令列を改めて取り込む | 実際の呼び出し先アドレスとロードしたコードに対して証明する | 抽出処理の信頼は残る。配置依存の証明の扱いが必要 |
| 限定した再配置の規則を証明する | 配置前の部品定理が、規則通りの配置・書き換え後にも適用できることを示す | 再配置種別、分岐範囲、シンボル対応の形式化が必要 |

最初は前者が小さく、将来の再利用では後者を検討できる。どちらも、関数名が一致するだけでは足りない。実際の分岐先と、そこのコード・契約・ABIを結びつける。

その上で、成果物ごとに命令列、契約、ISA・ABI、依存する定理、未解決の前提、検査器の版を記録する。**署名やハッシュは発行元・同一性の根拠であり、内容の正しさの証明ではない。** JSONの`proved`という文字を信頼する代わりに、対応する証明を実際に検査する構成を保つ。

**通過条件:** 再配置先の改変、同名の別実装、復帰先の破壊、保存状態の不一致を拒否する。スタックを使う場合はその領域を示し、呼び出しの費用も明示する。抽出器・リンカ・ローダーのうち、どの信頼が減り、どれが残ったかを報告する。

## 10. E6 — ISAモデルと、証明の実行環境を別方向から確かめる

### 10.1 使用命令だけで差分検査する

現在使っているロード／ストア、加算、比較、条件分岐、復帰に限定して、HOLモデル、独立した実行バックエンド、実機の結果を比べる。32ビットの書き込みによる上位ビット、フラグ、整列、境界付近のアドレスを重点的に扱う。

SailはISAの意味から実行可能なモデルや定理証明系向け定義、検査用の支援を生成する基盤で、Armのモデルもある。ただし、対象のArm版・命令・ツールの対応は先に確認する。現在のHOLモデルへそのまま接続できる前提にはしない。[Sailの公式説明](https://github.com/rems-project/sail)、[Sail Armモデル](https://github.com/rems-project/sail-arm)

実機で比べられるレジスタ・フラグ・メモリと、HOL側のイベント列を区別する。実機でモデル通りのアクセスイベント列をすべて直接観測できるとは限らず、キャッシュや投機の内部動作とも一致しない。未定義・非決定的な動作は、比較対象の条件をそろえる。

不一致を見つければ、モデル・デコード・試験ハーネスのどれに原因があるか切り分ける。一致する試験が増えても、全状態や全CPUでの対応を証明したとはしない。

### 10.2 別の検査器で証明を再検査する

次に、小さな定理一つについて、証明の出力・変換・独立したカーネルでの再検査が可能か調べる。s2n-bignumも独立した証明検査を信頼基盤への対策として挙げている。[健全性文書](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md)

定理の文を別の処理系へコピーするだけでは足りない。定義、型、使用公理、推論の対応も必要であり、出力・変換処理をどう検査するかが新しい問題になる。もう一つの処理系も同じ誤った仕様を確認している可能性は残る。

この方向は重要だが、最初からHOL Lightを置き換えたり、独自の論理カーネルを新造したりする作業には広げない。

## 11. E7 — ステップ数と、信頼しない最適化探索

### 11.1 終了の次に、資源の式を証明する

次の式は現在の命令列を数えた**証明候補**であり、今回新しく証明した定理ではない。

| 版・経路 | モデル上の命令ステップ数の候補 |
| --- | --- |
| 基本版コピー | `5n + 3` |
| 基本版埋め込み | `4n + 3` |
| 現在のコピー、`n != 8` | `5n + 5` |
| 現在のコピー、`n == 8`かつ整列 | `8` |
| 現在のコピー、`n == 8`かつ未整列 | `48` |

使用中のs2n-bignumにはステップ数付きの関係を扱う`common/relational_n.ml`があるため、まず再利用の可否を調べる。アクセスの回数・幅、使用レジスタ、スタック量も併記できる。

これで得られるのは、指定したモデルでの資源の式である。CPUのパイプライン、キャッシュ、OSの割り込み、ページフォルトを含む秒数の保証には、さらに別の前提が必要になる。命令数が少なければ必ず実時間も短い、とはしない。

### 11.2 候補生成器を、正しさの信頼基盤から外す

E1・E2が整った後なら、レジスタの選択、少数の命令の並べ方、ブロック幅等の有限な候補を探索し、**同じ契約を証明できた候補だけ**を性能比較へ残せる。

探索器は誤ってもよい。ただし、候補を受理する証明検査、仕様、モデル、最終命令列との対応は依然として信頼の要所である。証明に失敗した候補はE0の分類で未解決または反例ありと記録し、正しいか不明なものを採用しない。

CryptOptは、CPU上の測定を使うランダム探索と検証されたプログラム同値性の検査を組み合わせた前例である。Jasmin/EasyCryptにも、参照実装から最適化を段階的に同値性でつなぐ研究がある。ここから着想は得られるが、暗号の算術やx86の検査器を、そのままAArch64の任意のメモリ操作へ適用できるとはしない。[CryptOpt原論文](https://arxiv.org/abs/2211.10665)、[The Last Mile原論文](https://arxiv.org/abs/1904.04606)

評価は次を分ける。

- 短い呼び出しの遅延、大きなコピーの転送量、命令本体、配置の余白、証明・探索に使う時間。
- 暖まった小さなバッファと、より大きな作業領域。冷えたキャッシュをどのように近似したかも記録する。
- 探索中に見た入力・測定と、候補を固定した後の確認用の入力・独立した測定。

多数の候補から最速の測定値を選ぶだけでは、ノイズを選ぶこともある。探索後の測り直しを行い、速度・容量・証明費用のどれを優先するかを結果を見る前に決める。現在の7回測定の四分位による判定を、探索全体の統計的な信頼度の保証とは扱わない。

## 12. 前提が壊れる場合を、APIでどう表すか

ここまでの拡張でも、排他的なアクセスと通常RAMという前提は残る。さらに進める場合は、次のように実験を分ける。

| 扱いたいもの | 調べる最小の対象 | 保証の境界 |
| --- | --- | --- |
| データ競合 | 共有領域をロックや権限の移動で保護する呼び出し元 | 通常の`memcpy`自体を同時更新に安全としない。弱いメモリ順序を扱うなら対応するモデルが必要 |
| 部分的な失敗 | 途中のアクセス失敗時に、どの出力まで変わり得るかの契約 | ページ権限の変更・プロセス停止・物理故障まで含む全件原子的なコピーを勝手に保証しない。巻き戻し自体にも実行可能性の前提がある |
| 秘密データ | 同じ公開長・公開アドレスで、入力値を変えても同じモデル内の分岐・アクセスを行う性質 | 実時間、投機、電力等のあらゆる漏えいを防ぐこととは違う |
| 終端や初期化状態 | 容量と終端の存在証明を持つ文字列、有界の走査 | 情報を持たない裸のポインタから、有効範囲や終端を一般的に復元できるとはしない |
| 別ISA・別ABI | 共通のバイト仕様を保ち、別バックエンド一つで実装 | 機械モデル・保存レジスタ・リンカの条件は別に証明・検査する |

これらは「信頼を消す」以外に、**信頼する条件を型や効果で表し、条件を満たさない操作を構成できなくする**という言語設計の実験になる。

## 13. 前提と根拠を追跡する仕組み

将来の構築環境では、保証を単一の`safe`にまとめず、少なくとも次の軸を持たせたい。

| 軸 | 記録すること |
| --- | --- |
| 主張 | 機能、終了、アクセス、保存、資源、情報漏えい等のどの性質か |
| 対象 | 仕様・コードの版、命令列、ABI、配置、呼び出し元 |
| 論理上の条件 | 非重複、長さ、権限、寿命など、定理の前提に何があるか |
| 外部との対応 | ISAモデルと実機、OSが維持する権限等、メタレベルで何を信頼するか |
| 根拠 | 機械検査した定理、反例、有限の試験、性能測定、レビューのどれか |
| 供給元 | 前提を親の証明・型・検査・外部契約のどこで満たすか |

親は子の未解決の条件を引き継ぐ。ただし、すべての前提を文字列の集合として合併するだけでは不十分である。論理上の条件の導出は定理で行い、実機との対応の信頼や有限の測定は別の種類の根拠として扱う。

この情報から、ライブラリを使う側は「何が証明され、何を自分が満たす必要があり、何が外部への信頼として残るか」を確認できる。前提の表示を整えるだけで保証を強めたことにはせず、各実験でどこまで導出できたかを更新する。

## 14. 次の一回を小さく切るなら

最初の発展版は、次の順序が扱いやすい。

1. **E0:** 既存の破壊例に反例の根拠を付け、意味を保つ変形を一つ正例に加える。
2. **E1:** 固定レジスタのCopy8二つを合成し、16バイトの部品と直接記述の版が同じ命令列になることを確認する。
3. **E2:** その部品の考え方で任意長の8バイトループを一つ作り、元の公開契約を証明する。
4. **判定:** 機能・アクセス・終了・保存、実物との対応、証明の修正費用、速度・容量を別々に評価する。

この一回では、OS/ISA、ABI、メモリの並行性、論理カーネルを同時に変更しない。新しい機械語の前提を足さずに進められるため、結果の理由を見分けやすい。

合成がかえって重い、最適化が遅い、契約が増えすぎる、と分かった場合も有用な結果である。改善を確認できた部分を残し、次にE3の呼び出し元かE4の`memmove`へ進む。E5・E6はライブラリとして使う経路の信頼を減らす段階、E7の探索は部品と検査が安定した後の段階とする。

目指すのは、実装者がすべてを信じて組み立てる環境から、**根拠を再利用して組み立て、未解決の前提がどこに残ったかを検査できる環境**への発展である。
