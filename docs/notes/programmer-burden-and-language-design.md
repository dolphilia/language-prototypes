# プログラマーの負担から見るプログラミング言語と機能の分類

[メモの一覧へ](README.md) · [リポジトリの目次へ](../../README.md)

調査日: **2026-11-07**
更新日: **2026-11-07**（負担の変遷を比較する補足メモへのリンクを追加）

目的: プログラマーの仕事を楽にするために生まれた言語・言語機能を、**人間が何をしなくてよくなるのか、何を考えやすくなるのか**で分類し、言語設計の検討に使える形にまとめる。

方式の変化に注目した補足: [プログラマーの負担はどう移り変わったか](programmer-burden-transitions.md)。軽くなった点と、新規・移転・残存する問題を、歴史上の節目と比較表で整理している。

## 1. 調査の範囲と読み方

「負担を減らす」には、入力する文字数を減らすこと以外にも、機械の都合への対処、学習、状態の追跡、誤りの発見、資源の管理、変更の影響調査、共同作業を楽にすることが含まれる。本メモでは、汎用言語に加え、SQLのような特定用途の言語、型や所有権などの機能も対象にする。

次の二つを区別する。

- **資料で確認できる設計目的・仕組み**: 開発者の説明、原論文、公式文書に基づく。第2節では特に、目的が明示された例を取り上げる。
- **負担による分類・比較・設計への示唆**: 確認した仕組みを本メモで整理・解釈したもの。ある機能の有用性を、その言語全体が生まれた唯一の理由とは扱わない。

これは代表例による見取り図であり、全言語を網羅した一覧や、発明の優先順位を確定する年表ではない。また、設計者の意図や機能の存在は、実務での工数削減率を実証するものではない。特定の言語が常に最も楽だという順位付けは行わない。

言語仕様、標準ライブラリ、実行系、開発ツールが協力して実現するものもある。たとえばJavaの移植性にはJVMが、Erlangの障害対処にはOTPが関わる。`gofmt`は言語機能ではなく周辺ツールとして明記する。実装状況は参照資料に基づき、研究的な仕組みと広く実用化された仕組みを分けて説明する。

## 2. 負担軽減が設計目的として確認できる代表例

以下の時点は、誕生年に統一せず、目的を確認した資料や取り組みの時点を示す。

| 言語・取り組み | 資料の時点 | 明示された課題と目的 | 主に助ける仕事 |
| --- | --- | --- | --- |
| FORTRAN | 1950年代の開発を振り返るBackusの歴史論文 | プログラミングとデバッグの費用が大きく、それが計画の主要な動機だった。数式から効率のよい機械向けプログラムを生成する | 機械命令への翻訳、低水準の実装とデバッグ。[Backus, §§1.2–2](https://softwarepreservation.computerhistory.org/FORTRAN/paper/p25-backus.pdf) |
| Lispの自動記憶回収 | McCarthyの1960年論文 | 不要なリストを人間が追跡して消す方式より、自動回収の方が便利であると説明する | 解放対象と解放時点の管理。Lisp全体の誕生目的と、この機能の目的は区別する。[原論文の記憶管理の節](https://www-formal.stanford.edu/jmc/recursive/node4.html) |
| BASIC | 1964年の初版マニュアル | 教員・学生が機械語の学習に過大な時間を使わず計算機を利用できること、学びやすさ、高速なコンパイルなどを要件とした | 入門時の学習、初めて動くまでの作業。[初版マニュアル序文](https://www.dartmouth.edu/basicfifty/basicmanual_1964.pdf) |
| SEQUEL（SQLの前身） | Chamberlin・Boyceの1974年論文 | 専門家のプログラム作成・保守・変更の費用を減らし、非専門家にもデータベース利用を開く | データ取得手順の実装、問い合わせの習得。[原論文のIntroduction](https://course.ccs.neu.edu/cs5200f17/ssl/readings/boyce.pdf) |
| MLの多相型検査 | Milnerの1978年論文 | 多様な型の値を扱う柔軟さを維持しつつ、わかりにくい型の誤りを早く発見する | 再利用できる処理の記述と、型不整合のデバッグ。[Milner, Introduction](https://www.pure.ed.ac.uk/ws/files/15143545/1_s2.0_0022000078900144_main.pdf) |
| Python | Guido van Rossumの1996年の序文 | 読みやすさ、再利用、記法の不要なばらつきを減らすことを重視し、記述・デバッグに使う人間の時間に言及する | コードを読むこと、書き方の選択、他人のコードの再利用。[作者の説明](https://www.python.org/doc/essays/foreword/) |
| Java | 1996年のホワイトペーパー | 言語の単純さ・既存言語への親しみやすさと、異種環境への配布・移植を設計目標にする | 習得、信頼できる実装、環境ごとの移植。[単純さの設計目標](https://www.oracle.com/java/technologies/simple-familiar.html)、[移植性の設計目標](https://www.oracle.com/java/technologies/architecture-neutral-portable-robust.html) |
| ErlangとOTP | Armstrongの2003年の学位論文 | 誤りが残る大規模な通信ソフトウェアから、信頼できるシステムを構築する | 並行処理、障害の隔離、障害後の対処。言語とライブラリの分担も論じる。[論文のAbstract](https://erlang.org/download/armstrong_thesis_2003.pdf) |
| Go | Rob Pikeの2012年の設計解説 | 遅いビルド、制御しにくい依存関係、理解しにくいコード、更新費用など、大規模開発の問題を扱う | 個人の記述作業に加え、チームの開発・保守・更新。[設計解説の§§1–4](https://go.dev/talks/2012/splash.article) |
| Dafny | 公式チュートリアル | 正しいコードを書きやすくするため、実装が高水準の仕様を満たすことを検証する | 実装の正しさの確認。ただし正しい仕様を書く責任は残る。[公式Introduction](https://dafny.org/dafny/OnlineTutorial/guide) |

ここからわかるのは、「速く入力する」「初心者向けにする」だけが負担軽減ではないということだ。長期保守や信頼性の確保も、言語の設計対象になっている。

## 3. 負担の種類による12分類

分類は排他的ではない。たとえば所有権は資源管理と並行処理の両方を助け、型推論は入力と誤り検出の両方に関わる。下表の対応は本メモの整理であり、個別の根拠は後続の各節に示す。

| 分類 | プログラマーが負っていた作業 | 主な仕組み・代表例 |
| --- | --- | --- |
| A. 機械への翻訳・移植 | 計算を命令列へ落とし、環境ごとに作り直す | 高水準言語、コンパイラ、仮想機械。FORTRAN、Java |
| B. 問題から手順への変換 | 欲しい結果から、探索・走査・集計の手順を組み立てる | 宣言的記述、分野に合うデータ表現。SQL、Prolog、COBOL |
| C. 学習・読み書き・試行 | 記法を覚え、コードを読み、最初の結果を得る | 学びやすい構文、読みやすさ、対話環境。BASIC、Python、Ruby |
| D. 実行経路・状態の追跡 | どこから来て、どこがいつ変わるかを頭で追う | 構造化制御、不変データ、純粋関数 |
| E. 重複・定型記述 | 同じ処理や型違いの実装を何度も書く | 関数、高階関数、ジェネリクス、マクロ |
| F. 全体理解・変更の波及 | 内部実装を知り、変更の影響を調べる | モジュール、抽象型、カプセル化、インターフェース |
| G. 型情報の管理・誤用の発見 | 型を繰り返し書き、不整合を実行後に探す | 静的型検査、型推論、段階的な型の導入。ML、OCaml、TypeScript |
| H. メモリ・資源の寿命管理 | 解放時点、所有者、参照の有効性を追う | GC、RAII、所有権・借用。Lisp、C++、Rust |
| I. 欠損・失敗・場合分け | 特別な値の意味を覚え、処理漏れを防ぐ | nullable型、Option、Result、パターン照合、例外 |
| J. 並行処理・非同期処理 | 同期、待機、継続処理、タスクの終了を管理する | メッセージ通信、async/await、構造化並行処理、共有の静的検査 |
| K. 副作用・前提・正しさ | 呼び出しの作用や暗黙の前提を調べ、仕様への適合を確認する | エフェクト型、契約、自動検証。Koka、Eiffel、Dafny |
| L. チーム開発・反復待ち | ビルドを待ち、依存関係や書式、更新方法をそろえる | ビルドを意識した言語設計、標準的なツール。Goとその開発環境 |

### 3.1 A — 機械への翻訳・移植を任せる

高水準言語は、計算の意図と機械の実行方法の間を埋める。FORTRANでは数式などを記述し、その機械向けの命令生成をコンパイラへ任せる。重要なのは、翻訳作業の省力化に加え、人が手で調整する必要を減らせるだけの実行効率も目指した点である。[Backusの開発史](https://softwarepreservation.computerhistory.org/FORTRAN/paper/p25-backus.pdf)

Javaのバイトコードと実行系は別の負担を引き受ける。対象環境に対応する実行基盤があれば、プログラムごとにCPU向け命令へ移植する作業を減らせる。これは言語だけで完結する性質ではない。[Javaホワイトペーパー§4.1](https://www.oracle.com/java/technologies/architecture-neutral-portable-robust.html)

残る負担: アルゴリズムの選択、計算量、ハードウェア固有の最適化、OSや外部ライブラリへの依存は別に考える必要がある。「高水準だから性能を考えなくてよい」「仮想機械があればすべての環境差が消える」とは言えない。

### 3.2 B — 問題の表現を、分野や欲しい結果に近づける

| 仕組み・例 | 軽くなる作業 | 残る・新たな負担 |
| --- | --- | --- |
| COBOLの業務向け表現と十進固定小数点 | 業務データや金額を扱うための表現上の手間を減らす。英語に近い記述は読みやすさも狙う | 業務規則、精度、丸め、データ設計の判断は必要。冗長な記法が短い記法より常に楽とは限らない。[IBMの言語解説](https://www.ibm.com/think/topics/cobol) |
| SQLの集合的・宣言的な問い合わせ | 一行ずつの走査、結合、集計を組み立てる代わりに、対象と条件を記述する | スキーマ、結合条件、NULLや重複の意味は理解する。設計目的の根拠は[SEQUEL原論文](https://course.ccs.neu.edu/cs5200f17/ssl/readings/boyce.pdf) |
| Prologの関係記述、単一化、バックトラック | 候補の照合や、失敗時に別の候補へ戻る処理を実行系へ任せる | 通常の実行では節やゴールの順序が探索・停止性に影響する。効率や停止を完全に自動で決めてくれるわけではない。[SWI-Prologの用語集](https://www.swi-prolog.org/pldoc/man?section=glossary) |

たとえば、次のSQLは「支払済み注文の顧客別合計」を記述する例である。

```sql
SELECT customer_id, SUM(amount) AS total
FROM orders
WHERE status = 'paid'
GROUP BY customer_id;
```

どの順序で読み、どの方法で集約するかの計画はDBMSが選ぶ。ただし計画が期待どおりの性能になるとは限らず、`EXPLAIN`で調べる仕事は残る。[PostgreSQLの実行計画の説明](https://www.postgresql.org/docs/current/using-explain.html)

分類上の要点: 宣言的な言語は、**実行手順の実装を減らし、満たすべき条件の記述へ仕事を移す**。

### 3.3 C — 学習し、読み書きし、試せるようになるまでを短くする

BASICは、計算機の専門家でない学生・教員を対象に、容易な学習と短いコンパイル時間を要求した。BASICと同時に整備されたタイムシェアリング環境も利用のしやすさを支えた。対話性の利点を構文だけに帰属させるべきではない。[1964年の要件](https://www.dartmouth.edu/basicfifty/basicmanual_1964.pdf)、[Dartmouthによる開発の説明](https://www.dartmouth.edu/basicfifty/basic.html)

Pythonの作者は、インデントによるまとまり、書式の統一、不要な選択肢の削減を、読みやすさと関連づけている。助ける対象は初学者だけでなく、**後から他人のコードを読む人**でもある。[作者の序文](https://www.python.org/doc/essays/foreword/)

Rubyは自然に書けることを設計上の理想として説明している。これは、機能数を最小にすることとは別の、人間の表現のしやすさを重視する方向である。自然に感じるかどうかは利用者にも依存する。[Ruby公式の設計思想](https://www.ruby-lang.org/en/about/)

残る負担: 短く自然に書けることと、誤りを事前に検出できることは別の軸である。また、対話環境で小さな式を試せても、外部システムを含む挙動をすべて確認できるわけではない。

### 3.4 D — 実行経路と変化する状態を追いやすくする

**構造化制御**は、順次実行・分岐・反復などによって、ソース上の構造と実際の処理の対応をつかみやすくする。Dijkstraは、人間が時間的な過程を追う能力の限界を踏まえ、プログラムと実行過程の概念的な隔たりを小さくする必要を論じた。[EWD215](https://www.cs.utexas.edu/~EWD/transcriptions/EWD02xx/EWD215.html)

**不変データと純粋関数**は、同じ値が別の場所から書き換わっていないかを調べる負担を減らす。純粋な部分では、入力と結果の関係を中心に考えられる。Hughesは関数型言語の利点を、こうした性質に加え、高階関数や遅延評価による部品の組み合わせやすさから説明している。[Why Functional Programming Matters](https://www.cs.tufts.edu/comp/150FP/archive/john-hughes/whyfp.pdf)

Haskellにも入出力や処理順序が必要な操作は存在し、`IO`を使って純粋な値の計算と接続する。純粋関数による推論のしやすさを、システム全体に状態や時間の問題がないことと混同しない。[Haskell 2010 Report, Chapter 7](https://www.haskell.org/onlinereport/haskell2010/haskellch7.html)

残る負担: 状態を減らす代わりにデータ変換や作用の表現を学ぶ必要がある。コピー、共有、遅延評価に伴う時間・空間の挙動も、実装に応じて確認する必要がある。

### 3.5 E — 重複した処理と定型コードをまとめる

| 仕組み | 何を一度だけ書けばよくなるか | 主な代償 |
| --- | --- | --- |
| 関数・高階関数 | 共通手順を関数にし、手順の一部の違いも引数の関数として渡す。走査と各要素の処理などを分けて組み合わせる | 適切な分割と抽象化を設計する必要がある。[Hughesのモジュール性の議論](https://www.cs.tufts.edu/comp/150FP/archive/john-hughes/whyfp.pdf) |
| ジェネリクス・多相性 | 要素型だけが異なるコンテナや処理を、型ごとに複製しない | 利用可能な操作の制約を表現する必要がある。抽象的な型のエラーが難しくなる場合もある。[Rustのジェネリクス](https://doc.rust-lang.org/book/ch10-01-syntax.html) |
| マクロ | 通常の関数だけではまとめにくい構文上のパターンを、変換規則として記述する | 展開後の挙動や名前のスコープを理解する必要がある。Racketは展開のデバッガも用意する。[Racketのマクロ](https://docs.racket-lang.org/guide/macros.html) |

分類上の要点: 再利用を助ける機能は、**使う側の繰り返しを減らすために、共通部分を設計する側へ仕事を集める**。抽象化を増やすほど必ず負担が減るわけではない。

### 3.6 F — 全体を知らなくても部品を使い、変更できるようにする

Parnasのモジュール分割の議論では、変更されそうな設計判断を隠すことで、変更の波及と共同開発時の調整を抑える。単にファイルを分けることよりも、**利用者が知らなくてよい情報を決めること**が重要になる。[Parnasの1972年論文](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html)

| 仕組み・例 | 軽くなる作業 | 残る・新たな負担 |
| --- | --- | --- |
| モジュール・公開インターフェース | 利用可能な操作を確認すれば、内部のすべてを読まずに使える | 境界や公開範囲を適切に設計する。[OCamlのモジュール](https://ocaml.org/docs/modules) |
| 抽象データ型 | 内部の表現を隠し、正しい操作を通してだけ値を作り、変更する | 不変条件を維持する責任は、その型の実装に集まる。[OCamlの抽象型](https://ocaml.org/docs/modules#abstract-and-read-only-types) |
| クラスのカプセル化・多相性 | 状態と操作をまとめ、共通の呼び出し方で異なる実装を利用する | 継承や動的な呼び出し先を追う負担が生じうる。カプセル化の効果は公開範囲の設計による。[Javaのオブジェクトモデル](https://www.oracle.com/java/technologies/object-oriented.html) |

Eの「同じ実装を何度も書かない」と、Fの「実装を知らずに利用・変更できる」は関連するが異なる。再利用されていない部品でも、情報を隠すことで保守を助けられる。

### 3.7 G — 型の誤用を早く見つけ、型情報の重複記述を減らす

**静的型検査**は、値や操作の不整合の一部を実行前に見つける。**型推論**は、その検査に必要な情報を文脈から導き、型を何度も書く作業を減らす。後者は「型の規則をなくす」ことではない。[Milnerの多相型検査の論文](https://www.pure.ed.ac.uk/ws/files/15143545/1_s2.0_0022000078900144_main.pdf)

たとえばOCamlでは、次の関数の型を処理系が推論する。

```ocaml
let twice f x = f (f x)
(* 推論される型: ('a -> 'a) -> 'a -> 'a *)
```

プログラマーは、`f`が受け取る値と返す値の型の関係を、毎回明示しなくてよい。型は記述されていなくても存在する。[OCamlの型とパターン照合の説明](https://ocaml.org/docs/basic-data-types)

TypeScriptはJavaScriptに型の層を加え、既存コードの文脈からの推論や、明示的な型の導入を支える。既存資産を利用しつつ、誤用を見つけやすくする方向である。ただし完全な健全性を保証する設計ではなく、実行時のすべての誤りを防ぐわけではない。[公式入門](https://www.typescriptlang.org/docs/handbook/typescript-in-5-minutes.html)、[型システムの健全性に関する説明](https://www.typescriptlang.org/docs/handbook/type-compatibility.html#a-note-on-soundness)

残る負担: 型設計、推論結果の理解、型エラーへの対処が必要になる。型が合っていても、業務規則や計算式が正しいとは限らない。公開境界に型を明示することは、推論できる場合でも利用者の理解を助ける場合がある。

### 3.8 H — メモリと資源の寿命を管理する

| 方式 | 主に肩代わりする作業 | 人間が引き続き考えること |
| --- | --- | --- |
| トレーシングGC | 到達できなくなったメモリを検出し、回収する。Lispの初期論文にも自動回収の説明がある | 参照を保持し続ける設計、使用メモリ量、回収のコスト。メモリ回収だけでファイルなどの適切な終了時点も決まるわけではない。[McCarthyの記憶回収](https://www-formal.stanford.edu/jmc/recursive/node4.html) |
| RAII | ファイルやロックなどの資源をオブジェクトに結びつけ、破棄に伴う後始末を共通化する | 適切な所有者と寿命を設計する。C++のRAIIだけで、すべての参照の有効性まで静的に検査できるわけではない。[StroustrupによるRAIIの説明](https://www.stroustrup.com/bs_faq2.html#finally) |
| Rustの所有権・借用 | 所有の移動、破棄、参照の使い方を規則化し、危険な使用の一部をコンパイラが拒否する | 所有関係と共有の設計、借用規則の習得、検査が受け入れる形への整理。[所有権](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)、[借用](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html) |

これらは単純な新旧関係ではない。GCは共有されたデータの回収を実行系へ任せる方向で、所有権検査は許される使い方を静的に制約する方向である。RAIIはメモリ以外の資源にも適用できる。

「手動解放がない」「メモリ安全」「リークがない」「実行時コストがない」は別の性質として評価する必要がある。詳しい比較は既存の[所有権とその先](ownership-and-beyond.md)を参照。

### 3.9 I — 欠損・失敗・場合分けを見える形にする

| 仕組み・例 | 軽くなる作業 | 限界・代償 |
| --- | --- | --- |
| nullable型。Kotlinの`T`と`T?`など | 「ここはnullになりうるか」を型から確認でき、危険な直接アクセスを検出する | `!!`やJavaとの相互運用など、保証の外へ出る経路がある。[Kotlinのnull安全性](https://kotlinlang.org/docs/null-safety.html) |
| Optionなどの和型とパターン照合 | 「値がある／ない」などの状態を名前付きで表し、分岐を整理する。Rustの`match`は場合の網羅性を検査する | ワイルドカード分岐で変更を見逃す可能性や、各場合の処理自体の誤りは残る。[Rustのmatch](https://doc.rust-lang.org/book/ch06-02-match.html) |
| `Result<T, E>`と`?` | 成功値と失敗理由を区別し、失敗の伝播の定型処理を減らす | 回復方針は人間が決める。`unwrap()`などで失敗をpanicにすることもできる。[RustのResultと伝播](https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html) |
| 例外 | エラーが起きた場所から、対処できる呼び出し側まで伝える共通の仕組みを提供する | 制御の移動や後始末を理解する必要があり、何が送出されるかが型で表れるかどうかも言語によって異なる。[Pythonの例外処理](https://docs.python.org/3/tutorial/errors.html) |

これらは役割が異なり、併用される。たとえばKotlinのnull安全性は、通信失敗や任意の例外までなくす機能ではない。Rustの`?`も回復処理を自動生成するものではなく、主に伝播を短く書くための機構である。

### 3.10 J — 同時に進む処理と待機を扱いやすくする

「並行・非同期」を一つの問題として扱うと、何が楽になったのかが曖昧になる。

| 小分類・例 | 減らす負担 | 残る・新たな負担 |
| --- | --- | --- |
| メッセージ通信。Erlangのプロセス | 処理単位の状態を分け、共有状態を直接操作する代わりにメッセージで連携する | メッセージの順序、待ち合わせ、滞留、通信手順を設計する。[Erlangの並行処理](https://www.erlang.org/doc/system/conc_prog.html) |
| `async` / `await`。C#など | 待機後の処理を細かいコールバックへ分割せず、一連の文として記述しやすくする | 待機点、キャンセル、共有状態、並列度の制御は残る。非同期化がそのまま並列化になるわけではない。[C#の非同期処理モデル](https://learn.microsoft.com/en-us/dotnet/csharp/asynchronous-programming/) |
| 構造化並行処理。Swiftなど | 子タスクの寿命を親のスコープに結びつけ、完了待ちや終了時の扱いを局所的に理解できるようにする | すべてのタスク生成が構造化されるわけではない。キャンセルも協調的で、要求した瞬間の停止を保証しない。[Swift SE-0304（Swift 5.5で実装済み）](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0304-structured-concurrency.md) |
| 所有権と型による共有の検査。Rust | 一部の並行処理の誤りを、再現困難な実行時の問題からコンパイル時の問題へ移す | デッドロック、処理順序の論理ミス、外部システムとの整合性を一括して解決するものではない。[Rustの並行処理の設計目的](https://doc.rust-lang.org/book/ch16-00-concurrency.html)、[Mutexでも残る論理エラー](https://doc.rust-lang.org/book/ch16-03-shared-state.html) |

ErlangとOTPには、障害が起きたときの処理を隔離し、監視・再起動を組み立てる方向もある。これは競合を防ぐこととは別の負担軽減であり、再起動してよい単位や保持すべき状態を決める責任は残る。[Armstrongの論文](https://erlang.org/download/armstrong_thesis_2003.pdf)

### 3.11 K — 副作用、暗黙の前提、仕様への適合を確認する

| 仕組み・例 | 見えるようにする情報・自動化する作業 | 限界・代償 |
| --- | --- | --- |
| 契約。Eiffelの事前条件・事後条件・不変条件 | 呼び出し側の義務と実装側の保証を記述し、違反時の問題の所在を判断しやすくする | 契約を書く作業が必要。実行時の契約検査と、すべての実行に対する静的な証明は異なる。[Eiffelの契約](https://www.eiffel.org/doc/solutions/Design_by_Contract_and_Assertions) |
| エフェクト型。Koka | 関数の潜在的な作用を型に表し、呼び出し先の実装を全部読まなくても作用を判断する材料を得る。型と効果の推論も行う | 効果の意味やハンドラなどを学ぶ必要がある。ここでの根拠は実装を伴う研究成果であり、他の言語一般の標準機能とは扱わない。[Kokaの原論文の説明](https://www.microsoft.com/en-us/research/publication/koka-programming-with-row-polymorphic-effect-types/) |
| 仕様に基づく自動検証。Dafny | 事前・事後条件、ループ不変条件などを基に、実装が仕様に合うことや、一部の実行時誤りがないことを検証する | 仕様の正しさ、十分な注釈、検証器への補助、検証対象外との接続の確認は残る。[Dafnyの公式ガイド](https://dafny.org/dafny/OnlineTutorial/guide) |

たとえば「入力は0以上」「結果は入力以上」「この関数はどの作用を起こしうるか」を機械が扱える情報にすると、実装を読むたびに人が推測する必要を減らせる。ただし、書いた仕様が利用者の本当の要求を表しているかは別問題である。

分類上の要点: **正しさを考える仕事をなくすのではなく、明示した条件から確認できる部分を機械へ渡す**。

### 3.12 L — チームで開発し、変更を反映する負担を減らす

Goの設計解説は、ビルド待ち、依存関係、更新、コード理解といった問題を明示している。負担軽減の単位を「短い関数を書く一人」から「長期間にわたり一つのシステムを変更する多数の人」へ広げた例として読める。[Pikeの設計解説](https://go.dev/talks/2012/splash.article)

同じ解説は、`gofmt`が書式の議論を減らし、他人のコードを読みやすくすることにも触れる。これは**言語の周辺ツール**であり、文法に内蔵された機能ではない。言語の構造が自動整形・解析・変更を行いやすいことと、ツールが普及することが組み合わさって効果を生む。

残る負担: ビルド速度はコード量、依存先、ツールチェーン、実行環境による。標準的な書式があっても、命名、API設計、依存関係の妥当性まで自動的に統一されるわけではない。

## 4. 横断比較 — 負担はどこへ移るのか

以下は、第3節の事例から本メモで導いた比較である。同じ自動化でも、人間の作業が減る場所と増える場所が異なる。

| 軽減の方法 | 代表例 | 人が減らせる作業 | 移った先・増えうる作業 |
| --- | --- | --- | --- |
| 実行系へ任せる | GC、Prologの探索 | 解放対象の追跡、候補を戻す処理 | 実行時間・メモリのコスト、実行時挙動の観測 |
| コンパイラへ任せる | 型推論、所有権検査 | 注釈の反復、一部の不整合や参照誤用の発見 | 検査規則の理解、拒否されたコードの整理 |
| 抽象化の提供者へ集める | 関数、モジュール、ジェネリクス、マクロ | 同じ処理の再実装、内部実装の読解 | 抽象化・公開境界・診断の設計 |
| 目的・条件を記述する | SQL、契約、Dafny | 実行手順や適合確認の一部 | 正しい要求・条件・データモデルを書く作業 |
| 許される状態や順序を絞る | nullable型、不変データ、構造化並行処理 | 危険な状態や自由な順序を個別に追跡する作業 | 制約に合う設計、明示的な例外処理 |
| 選択肢をそろえる | 一貫した記法、自動整形 | 書式選びや表現のばらつきへの対応 | 方針への習熟、特殊な要求との折り合い |

このため、コードが長くなっても負担が下がることはある。`Result`の分岐や契約を明記することで、後から失敗や前提を調べる手間が減る場合がある。一方、非常に短いマクロや宣言的な式でも、展開や性能の理解が難しい場合がある。

評価する対象は、記述量だけでなく、**学習・実装・読解・デバッグ・変更を通した仕事量**である。

## 5. 言語設計への示唆と検証の観点

ここからは本メモの考察であり、このリポジトリの確定仕様ではない。

### 5.1 最初に「何を覚えていなくてよくするか」を決める

| 減らしたい負担 | 検討する設計 | 効果を確かめる観点 |
| --- | --- | --- |
| 解放と参照の有効性を追う | GC、RAII、所有権・借用を用途に合わせて選ぶ | 資源誤用の数、実装時間、診断の理解時間、実行時コスト |
| 欠損・失敗を覚えて処理する | 欠損と失敗を区別し、網羅性検査と伝播構文を整える | 処理漏れ、回復方針の読み取りやすさ、分岐の記述量 |
| 型を何度も書く | 推論と公開境界の明示を組み合わせる | 注釈量、変更時の修正量、型エラーの修正時間 |
| 状態の変化と作用を追う | 不変性を基本にする、変更や作用の境界を示す | 一つの処理を理解するために調べる箇所、状態に関わる誤り |
| 同時進行する仕事の終了を管理する | タスクの寿命、待機、キャンセルを構造化する | 終了しない処理、残存タスク、キャンセルのテストしやすさ |
| 他人のコードと変更を理解する | モジュール境界、公開API、整形・解析ツールを整える | 変更の影響箇所、レビュー時間、初回ビルドまでの時間 |

初学者と熟練者、小さな試作と長期保守、ライブラリの利用者と作者では、軽くしたい仕事が異なる。対象を決めずに機能数だけを増減させても、負担軽減は評価できない。

### 5.2 安全な使い方を日常の書き方にする

安全にするための機能があっても、毎回複雑な宣言や定型コードを要求すれば、利用者は負担を感じる。型推論、簡潔なエラー伝播、資源の自動後始末、よい診断は、安全性の規則を実際に使えるものにするための設計として評価する。

同時に、自動化した判断を確認できる必要がある。推論された型、マクロ展開、実行計画、タスクの構造などが見えれば、期待と違う場合に原因を追いやすい。機能の導入と、その挙動を説明する手段を一緒に検討したい。

### 5.3 比較では、減った作業と増えた作業を両方測る

たとえば新しい所有権機能を検討するなら、手動管理で起きる誤りだけでなく、借用エラーの理解やデータ構造の変更にかかる時間も見る。宣言的な仕組みなら、初回実装の短さだけでなく、性能調整や要求変更の難しさも見る。

この調査からは、万能な一つの仕組みを選ぶより、**対象のプログラマーが繰り返し担う作業を特定し、どの部分を機械・抽象化・規則へ渡すかを決める**ことが、設計の出発点になると考えられる。
