## 1. 現時点での考え

私の見通しは、次の三点である。

1. **「この種類の処理は、どんな言語・証明技術を使ってもunsafeでなければ書けない」という、固定的な操作の一覧は考えにくい。** ポインタ操作、メモリ確保、並行処理、機械語の実行であっても、適切な情報と証明を伴えば、検証する仕組みを設計できる。
2. **実用的なシステムには、検証を省略した実装や、外部の振る舞いを信頼する接続部分が残りやすい。** 現在のunsafeに相当する責任は、そうした部分へ集中すると考える。
3. **unsafeという構文がゼロであることと、信頼する前提がゼロであることは違う。** 言語仕様、証明の基盤、実行基盤、物理的な機械との対応には、明示すべき前提がある。

したがって、「最後まで残る命令は何か」より、**最後まで証明せずに受け入れる条件は何か、その条件を誰が引き受けるか**を問うほうが、言語設計には役立つと考える。

これは、任意のプログラムを自動的に安全に変換できる、あるいは将来の型システムがすべての正しいコードを受け入れられる、という主張ではない。安全に書くためには、API、データ表現、実行方法を変える場合もある。

## 2. unsafeをなくすには、複数の意味がある

### 2.1 利用者が書かなくてよくなる

GhostCellの利用者は、データを変更する権限をトークンの借用で表せる。利用者の各操作にunsafeを要求する代わりに、型検査に条件の一部を任せられる。

ただし、現在のRustライブラリとしてのGhostCellの内部にはunsafeがある。利用者から見えなくなったことと、実装から消えたことは別である。[GhostCellの原論文](https://plv.mpi-sws.org/rustbelt/ghostcell/paper.pdf)、[詳細メモ](ghostcell.md)

### 2.2 実装の条件も、別の検証系で証明する

ライブラリ内部で生ポインタを操作していても、その実装が権限と不変条件を保つことを論理で証明できる。RefinedRustには、unsafeな操作を含む`Vec`の変種を検証する研究がある。[RefinedRust](https://plv.mpi-sws.org/refinedrust/)

この場合、Rustのソースには`unsafe`が残っていても、「通常のRustコンパイラが確認しない条件」を、別の機械検証で扱っている。さらに将来の言語なら、その証明を受け付ける低水準構文を用意し、未検証のunsafeと区別することも考えられる。

### 2.3 言語の安全な基本操作として提供する

たとえば、メモリの確保を安全な基本操作として持つ言語では、利用者は割り当て処理の内部をunsafeで書かない。基本操作の仕様と、その実装が正しいことが言語・処理系の責任になる。

その実装も検証すれば、単に大きな未検証部分へ押し込めるより強い根拠を得られる。ただし、基本操作を仕様へ追加しただけで、既存の実装の正しさが証明されたことにはならない。

この三つを分けないと、「unsafeはすでに不要」と「結局どこかに必ず必要」が、違う範囲について語る議論になってしまう。

本メモでいう安全性は、主にメモリ安全性や未定義動作の防止である。安全なAPIがエラーを返すことや、実行を中止することはありうる。計算結果の正しさ、停止の保証、外部への操作が適切かという性質まで、自動的に含めるわけではない。

## 3. 通常のデータ操作に、固定的な境界は見えない

従来unsafeを使う動機になっていた処理の多くは、安全条件をより適切に表すことで、別の書き方へ移せる。

| 処理 | 別の記述へ移す方向 | 残る検討事項 |
| --- | --- | --- |
| 複数の参照を持つグラフの変更 | GhostCellのように、到達する経路と変更権限を分離する | 権限機構そのものの実装と証明 |
| 配列の領域を分けて同時に変更 | 分割API、範囲の証明、領域ごとの権限 | 領域が重ならない根拠 |
| 未初期化領域を順に埋める | 初期化状態を追う型・証明 | 中断時の状態と、破棄の整合性 |
| 自己参照や侵入型データ構造 | アドレスの安定性と、移動・破棄の条件を明示する | 参照先の生存期間と構造全体の不変条件 |
| 独自のアロケータやプール | 所有する領域、分割、回収を論理で追う | 割り当て領域の重複や二重回収の防止 |
| ロックフリーなデータ構造 | 原子操作、回収方式、共有権限を含む検証 | 実行モデル、メモリ順序、回収の条件 |
| バイナリの解釈や変換 | レイアウトと値の有効性を検査するAPI、検証済みの変換 | 任意のバイト列を任意の型として扱わないこと |

ここで示したのは設計の方向であり、上のすべてに、現在のRustで使える完成済みの統一機構があるという意味ではない。関連する既存の仕組み・研究は、[unsafeの発展](unsafe-and-beyond.md)で整理している。

重要なのは、「コンパイラが現在理解できない」と「原理的に安全条件を記述できない」を分けることである。

また、検証可能にするには常に実行時検査を増やす必要がある、とも限らない。静的な証明や、実行時に消える証拠を利用する方向もある。制約が残るとすれば、主に表現力、証明・保守の労力、処理系の複雑さなどとの兼ね合いになる。[証拠を伴う低水準コードの研究](https://www.cs.cmu.edu/~fox/pcc.html)

## 4. 実用的には、どこに残りやすいか

以下は、将来も絶対にunsafeであるという分類ではなく、検証対象へ含めにくい条件や、未検証の責任が集まりやすい場所についての予想である。

### 4.1 契約を検証していない外部実装との接続

FFIで接続するCの関数が、「渡したバッファの外には書かない」「戻った後はポインタを保持しない」と約束しているとする。

呼び出し側の型が正しくても、外部実装がその約束を守ることまでは、それだけではわからない。ここには、次の選択肢がある。

- 外部実装も、共有する仕様に対して検証する。
- 外部実装を隔離し、境界を越える値を検査する。
- 管理された実行環境に置く、または別の実装へ置き換える。
- 契約が正しいことを、未検証の前提として受け入れる。

最後の選択が、unsafeに相当する責任として残りやすい。隔離の場合も、ライブラリ内部の正しさと、ホストへ被害が伝わらないことは別の保証になる。[FFIの宣言者の責任](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-extern.html)、[RLBoxの境界設計](https://www.usenix.org/conference/usenixsecurity20/presentation/narayan)

したがって、「FFIだから本質的にunsafe」ではなく、「**接続先を含む契約を検証も強制もしていないまま接続すること**」が、未検証の責任を残すと考える。

### 4.2 ハードウェアやOSの振る舞いと結び付く部分

MMIO、DMA、割り込み、ページテーブル、キャッシュやTLBの管理では、言語内の値だけでなく、機械やOSの規約も関わる。

たとえばDMAでは、CPUがバッファへアクセスしてよい期間、装置がアクセスする期間、書き込みが相手に見える条件を区別する必要がある。しかし、このことから、DMAの利用者が必ずunsafeを書くとは言えない。

実例として、2026年のTockは、`DmaSlice`と`DmaFence`によって、バッファをDMAへ渡して取り戻す規律を導入している。一方、アーキテクチャに合うフェンスの生成や、装置がアクセスしなくなったことの保証には、unsafeな責任が明示されている。[TockのSafe DMAの説明](https://tockos.org/blog/2026/talking-tock-63/)

残りやすいのは「DMAをする」という操作全体ではなく、たとえば次の接続条件である。

```text
このレジスタ操作で、本当にDMAが停止する。
このフェンスで、この機種の書き込みが相手へ見える。
このメモリ領域は、指定した属性で割り当て・マッピングされている。
```

これらも、装置モデルと実装を検証すれば、未検証部分を減らせる。ただし、実際の機種・設定がそのモデルに対応するという条件は別に確認する必要がある。

### 4.3 外部の資源へ、最初の権限を結び付ける部分

メモリ領域、デバイス、スレッド、外部オブジェクトなどを、一意の権限トークンとして扱う場合、「このトークンが実際の資源を正しく表す」という根拠が必要になる。

たとえば、数値のアドレスから「この領域を排他的に所有する」という値を作るだけでは、別の所有者がいないことを示せない。OSの割り当て結果、ブート時のメモリ配置、ランタイムの管理表など、信頼できる発行経路が必要になる。

ただし、**権限を最初に発行する操作が、必ずunsafeでなければならないわけではない。** 型を持つ基本操作、検証済みの発行器、実行時の管理機構として設計できる。残るのは、発行器の外にある資源との対応を、どこで保証するかである。

ブランドを新しく作るような言語内部の操作と、実際の装置への排他的なアクセス権を宣言することも、同じ問題として扱わないほうがよい。

### 4.4 外部の主体が、後から不変条件を壊せる共有資源

ファイルをメモリへマッピングし、通常の不変なバイト列として公開する場合を考える。別のプロセスが、そのファイルを変更・切り詰めできるなら、作成時にサイズを確認するだけでは、利用中の条件を保てない。

`memmap2`の通常のファイルマッピングAPIには、こうした理由によるunsafeの契約がある。一方、調査時点の公開ドキュメント（0.9.12）には、OSの仕組みによってファイルの不変性を確認する`map_if_safe`もある。文書では、sealed memfdやfs-verityなどを利用する構成が説明されている。[通常の`map`の契約](https://docs.rs/memmap2/latest/memmap2/struct.Mmap.html#safety)、[`map_if_safe`の条件](https://docs.rs/memmap2/latest/memmap2/struct.MmapOptions.html#method.map_if_safe)

これは、unsafeを安全な方式へ置き換える際に、型の工夫だけでなく、**外部からの変更を防ぐ権限・実行基盤の仕組みも必要になる**例である。条件を強制できない範囲まで、同じ保証を与えることはできない。

### 4.5 検証していない機械語を、実行可能なコードとして扱う部分

JITの生成結果やロードしたバイナリを、関数として実行する場面にも、責任が集中しやすい。

Wasmtimeの開発指針は、生成したコードを呼び出す接続部分が、コード生成器などの正しさへ依存すると説明している。現在の実装では、unsafeを残す実用上の理由になる。[Wasmtimeのunsafeに関する指針](https://docs.wasmtime.dev/contributing-coding-guidelines.html#use-of-unsafe)

ただし、これを機械語一般の原理的な限界とは考えない。生成コードへ安全性の証拠を付けて検査する方法もある。未検証のコード生成結果を信頼することと、証拠を検査してから受け入れることは違う。後者は7節で扱う。

### 4.6 証明・実装・保守の費用を、現時点では払わない部分

複雑なメモリ回収方式、特殊なレイアウト、独自アロケータ、命令セット固有の最適化などでは、検証できる見通しがあっても、実用上の費用が高い場合がある。

そのような箇所で、検証済みの抽象化が整うまでunsafeを選ぶことは残ると予想する。ただし、これは技術的・経済的な選択であり、「安全な方法では表現不能」という結論ではない。性能上必要という主張も、特定の言語・実装・費用条件について評価する必要がある。

## 5. 情報や権限が不足するAPIは、そのままでは安全にできない

### 5.1 任意の整数アドレスを読む関数

次の擬似APIを考える。

```text
read_word(address: 整数) -> 32ビット整数

要求:
  どんな整数でも受け取る。
  その数値が示す実メモリを、必ず読み取って返す。
  エラーにも、停止にも、隔離にも逃がさない。
  呼び出し側の追加条件も要求しない。
```

無効なアドレスも入力できる実行環境で、この要求をそのまま満たす安全なAPIは作れない。型システムが賢くなっても、入力に含まれない権限や生存の根拠を、整数だけから作り出せるわけではない。

Rustのポインタについても、数値のアドレスとprovenanceを区別するモデルが、この問題を考える手がかりになる。[標準ライブラリのProvenanceの説明](https://doc.rust-lang.org/std/ptr/index.html#provenance)

### 5.2 安全にするには、何かを変える

| 変更するもの | 安全な方向への変更例 |
| --- | --- |
| 引数 | 整数の代わりに、生存と範囲が管理された領域への権限を受け取る |
| 結果 | 実行基盤が検証・保護できる範囲を読み、失敗を結果として返す |
| 実行先 | 実メモリでなく、管理された仮想メモリのモデルを読む |
| 実行条件 | 所有する登録済み領域だけに対象を制限する |
| 契約 | 有効な領域を指すことを呼び出し側へ要求する |

最後の方法だけを、証明なしで受け入れるなら、unsafeに相当する境界が残る。契約の証拠も引数として受け取り、機械で確認できるなら、別の記述へ移せる。

なお、「アドレスが使えるか先に検査する」と書くだけでは不十分である。検査後の解放や権限変更を防ぐ、あるいはアクセス自体を安全に失敗させる仕組みまで必要になる。

### 5.3 外部データのバイト列も、同じ構造を持つ

任意の受信データを、「有効なオブジェクトである」と無条件に扱うことはできない。安全なデコード、検証済みの変換、型が要求する条件に合うデータ形式などを使う必要がある。

ここで残るのは「デコードはunsafe」という制約ではない。**必要な情報の検査を一切行わず、根拠も受け取らず、強い型の保証だけは得たい、という要求が成立しない**のである。

## 6. 自動検証の限界は、unsafeの必然性を意味しない

### 6.1 任意のコードを、正確に自動判定することには限界がある

一般のチューリング完全な言語の任意のプログラムについて、「不正なメモリアクセスを起こさない」といった性質を、必ず停止する手続きで完全に判定することはできない。たとえば、停止問題との関係を、次の抽象的なプログラムで考えられる。

```text
ある計算Mを、安全な方法でシミュレートする。
Mが停止したら、必ず不正なメモリアクセスをする。
```

無限に実行できる通常の計算モデルで、このプログラムが不正アクセスを起こさないことを完全に判定できれば、Mが停止しないことも判定できてしまう。これは、任意のコードの安全性を自動的に見抜く仕組みに限界があることを示す。

Proof-Carrying Codeの研究も、任意のコードの安全性を受信側が自力で判定する代わりに、コードの提供者へ検査可能な証拠を要求する方向を取る。[Automated Techniques for Provably Safe Mobile Code](https://www.cs.cmu.edu/~fp/papers/tcs00.pdf)

### 6.2 そこから「unsafeが不可欠」とは導けない

検査器が判断できない場合、言語や開発者には複数の選択肢がある。

- その記述を受け入れず、別の形で書いてもらう。
- 機械で確認できる追加の証明や注釈を要求する。
- 実行時検査や管理された表現を使う。
- 許すプログラムや資源を制限する。
- 未検証の仮定を受け入れる機能を設ける。

最後の選択肢がunsafeに近い。**自動判定の限界は、最後の選択肢を言語へ必ず搭載せよという定理ではない。**

追加の証明を要求する方法にも、固定した論理体系の表現力や証明探索の限界、工数がある。「証明が与えられたときに検査できる」と「すべての安全なプログラムの証明を自動で作れる」は違う。

## 7. 機械語やハードウェア操作も、原理的な例外ではない

### 7.1 機械語に、検査可能な証拠を付けられる

Proof-Carrying Code（PCC）やTyped Assembly Language（TAL）は、低水準コードへ安全性の証拠や型の情報を付け、受け入れる側で検査する研究である。[PCCの研究紹介](https://www.cs.cmu.edu/~fox/pcc.html)

この事実から、少なくとも「機械語だから安全性を論理で扱えない」という分類は適切ではない。対象の命令セット、メモリ、呼び出し規約などのモデルに基づいて、許される実行を検証する道がある。

本メモは、現在のPCCやTALが、あらゆるJITやアセンブリをそのまま検証できるとは主張しない。重要なのは、表現が低水準であることと、証拠を検査できないことは同義でない点である。

### 7.2 信頼する基盤の範囲も縮められる

たとえばPCCの研究には、従来信頼していた高水準の証明規則についても、より低水準の方針との関係を証明することで、信頼する基盤から外す取り組みがある。[Proof-Carrying Code with Untrusted Proof Rules](https://people.eecs.berkeley.edu/~necula/ISSS02/)

seL4も、対応する構成では生成バイナリを検証し、コンパイラとリンカの正しさをそのまま仮定する必要を減らしている。一方、機械の動作や初期状態などには明示された前提がある。[seL4の証明の前提](https://sel4.systems/Verification/assumptions.html)

したがって、「最後はコンパイラを信じるしかない」「ブート処理は検証不能」と固定するのも早い。検証の終点は、研究と実装によって動かせる。

## 8. 最後に残るのは、モデルと実際の実行を接続する前提

### 8.1 形式的な保証は、モデルと仮定に対する保証である

```text
安全性の仕様
    ↓
ソースコード・中間表現・機械語のモデル
    ↓
実装が仕様を満たすことの証明
    ↓
実際にロードされたコード、初期状態、機械での実行
```

上の関係の多くは、さらに検証できる。命令セットやハードウェア設計もモデルに含められる。

それでも、実物が対象のモデルに従い、必要な設定・初期状態が成り立つという接続は必要になる。seL4も、個々の未検証コードは原理的に検証へ移せる一方、物理世界についての前提まで数学の証明だけで消せるわけではないと説明している。[seL4の前提に関する説明](https://sel4.systems/Verification/assumptions.html#what-do-these-assumptions-mean)

### 8.2 前提が残ることと、危険なソース構文が必要なことは違う

言語処理系が、「このハードウェア契約の下で、この基本操作は安全」という形で提供すれば、利用者のプログラムにunsafe構文が現れる必要はない。処理系の実装も検証できれば、そのソフトウェア内部の未検証部分も減る。

安全性の前提があることを、直ちに「どこかに必ず生ポインタを自由に扱う抜け道が必要」と言い換えることはできない。前提は、仕様、対応プラットフォーム、初期化手順、検証済みの基本操作などで表せる。

また、メモリ安全な言語にも物理的な前提はある。その意味での信頼が残ることは、通常の安全なコードと未検証のunsafeコードの区別を無意味にしない。

### 8.3 未検証の仮定は、名前を変えても残る

一方、unsafeを禁止して、代わりに任意の条件を受け入れる`assume`や、検証をしない外部契約を自由に導入できるようにしただけなら、責任は移動しただけである。

評価すべきなのは、構文の出現数に加え、次の点だと考える。

- 安全性に関わる条件が、どれだけ型・証明・実行時の仕組みで保証されるか。
- 残る未検証の仮定が、どこに、どの範囲で存在するか。
- その仮定を変更できる主体と、破られた場合の影響が限定されているか。

## 9. 安全でない動作を、unsafeで正当化することはできない

解放済みの領域を有効な値として読むことや、必要な規則に反して同じ値を同時に変更することを、そのまま安全な機能として追加することはできない。

Rustでも、unsafeは未定義動作を許可する機能ではない。条件を守る責任を引き受けるための機能である。[Rust Reference](https://doc.rust-lang.org/reference/unsafe-keyword.html)

「どうしてもunsafeでしか書けないもの」として考える対象が、実際に保証へ反する動作なら、それはunsafeで解決する問題でもない。意味を変える必要がある。

たとえば、解放後も古い内容を読みたいなら、値を保持する期間を延ばす、スナップショットを残す、管理されたハンドルから失効を検出する、といった別の意味にする。任意のアドレスを操作するプログラムを研究したいなら、エミュレータ内のメモリを対象にする方法もある。

低水準の「何でもできる自由」と、安全性の「何が起きないかという保証」は、同じ対象・同じ意味のまま無制限に両立するものではない。

## 10. このリポジトリの言語設計への示唆

以下は設計案であり、採用決定ではない。

### 10.1 一つのunsafeへ、すべての責任を集めない

安全条件が通常の型検査で扱えない場合には、まず次を区別できるとよい。

| 状況 | 設計上の対応 |
| --- | --- |
| 必要な権限や状態を、型で表せる | 権限トークン、typestate、領域の型などを使う |
| 型だけでは足りないが、証明を付けられる | 低水準操作へ、検査可能な証拠を渡す |
| 実行基盤が条件を検査・強制できる | 管理された資源や、失敗を表すAPIへ接続する |
| 外部の仕様を仮定する必要がある | 対象、契約、前提を限定した接続点を設ける |
| 検証せずに引き受ける必要がある | 未検証であることと、引き受ける条件を明示する |
| 条件自体が成立しない | その記述を拒否するか、目的を別の意味で実現する |

「証明付きの低水準操作」と「証明せずに信頼する操作」は、同じ低水準の命令を生成していても、利用者への説明と監査上の扱いを分けたい。

### 10.2 不足している条件を、問いとして残す

新しいunsafeが必要になったとき、次の問いを記録すると、後から置き換える技術を検討しやすい。

1. その操作を正当化する条件は何か。
2. 条件は局所的か、利用期間全体にわたるものか。
3. 条件を壊せるのは、同じモジュールか、別スレッドか、OSか、装置か。
4. 型や権限を追加すれば、その主体を制限できるか。
5. 証明や実行時検査で確認できるか。
6. それでも仮定として残すなら、どの契約に限定するか。

### 10.3 残す機能の大きさは、言語の目的によって変わる

アプリケーション向けの言語なら、任意の未検証コードを実行する抜け道を公開せず、管理された基本操作だけで必要な機能を提供する選択がある。

処理系やOSも書くシステム言語なら、新しい装置や外部ABIへ接続するため、限定した信頼の宣言を用意する価値がある。さらに、証明を記述できる言語なら、その宣言の多くを証拠付きの実装へ移す方向を取れる。

どこまで許すかは設計上の選択である。汎用的なunsafeを持たせることだけが、システムを実装する唯一の方法だとは考えない。

## 11. 見通しと確認範囲

### 11.1 私が残ると予想するもの

| 残り方 | 見通し |
| --- | --- |
| アプリケーションの通常のデータ操作 | 多くは、新しい型・権限・安全なAPIへ移せると考える |
| 特殊なデータ構造や最適化の内部 | 証明の費用や処理系の対応範囲から、実用上は残りやすい |
| 未検証の外部実装や新しい装置との接続 | 契約を仮定する境界が残りやすい。検証・隔離・権限制限によって縮められる |
| コードや資源を、安全な世界へ受け入れる部分 | 証拠や強制機構を持たなければ、信頼の責任が残る |
| モデルと実機の対応、論理・証明検査の基盤 | 前提を明示する必要がある。ただしunsafe構文が不可避であることは意味しない |

「本質的にunsafeな操作の小さな集合が最後に残る」というより、**検査可能な根拠を持たせた操作が増え、その外にある未検証の契約と環境の前提へ、責任が集まる**と考える。

### 11.2 事実と、まだ主張できないこと

GhostCell、RefinedRust、PCC/TAL、TockのDMA抽象化、`memmap2`のAPI、Wasmtime、seL4の資料を確認し、その事実を根拠に考察した。

これらを統合した万能の言語がすでに存在すること、現在のRustからunsafeをすべて除去できること、任意の安全なプログラムを実用的な費用で検証できることは、主張していない。

コードのビルドや性能測定、新しい検証方式の実装は行っていない。`text`ブロックは、考え方や要求を明確にするための擬似記述である。
