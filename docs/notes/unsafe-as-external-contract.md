## 1. 最終的な形の見通し

この仮定の下では、unsafeは、**「この外部実装・装置が、この契約に従うことを、この接続点で引き受ける」という宣言**へ収束すると考える。

その宣言を通じて、内部コードが利用できる、型付きの操作・権限・状態を受け取る。利用中の所有、借用、初期化、領域の分割などは、仮定どおり内部の検証で扱う。

結果として、中心になるのは次の三つである。

1. **外部契約**: 相手が何を守る必要があるか。
2. **接続の根拠**: 証明、実行時の強制、未検証の信頼のうち、何に依存するか。
3. **利用権限**: 内部のどのコードが、どの資源へ、いつアクセスできるか。

現在のunsafeブロックのように、任意の関数の途中で追加の責任をまとめて引き受ける形式は、中心ではなくなると予想する。日常的な利用では通常の型検査を使い、未検証の前提を受け入れる場所を、外部との接続に限定する。

## 2. 外部と保証を、どう定義するか

### 2.1 外部とは、保証に必要な振る舞いを検証していない相手である

ここでの境界は、プロセスやプログラミング言語の境界と一致するとは限らない。

検証されていないCライブラリは、同じプロセスでも外部になりうる。一方、別プロセスとの通信でも、受信内容を任意のバイト列として安全に扱えるなら、その内容を信用する必要はない。

また、内部の未検証コードを「外部」と呼び直すだけでは、今回の仮定を満たしたことにならない。内部について何を検証したか、相手が何へ干渉できるか、どの契約を受け入れているかを具体的に定める。

### 2.2 二種類の保証を区別する

| 保証 | 意味 | 外部が契約を破った場合 |
| --- | --- | --- |
| 条件付きの保証 | 外部契約Aが成り立てば、内部を含む実行は安全 | 保証の前提が外れる |
| 境界で保護された保証 | 境界が許す範囲で外部がどう振る舞っても、内部の指定した安全性は保たれる | エラー、隔離先の停止、拒否などとして扱える設計にする |

後者にも、隔離機構や実行基盤が仕様に従うという前提はある。「任意の物理故障が起きても絶対に安全」という意味ではない。また、隔離先の内部まで安全だと主張するものでもない。

型付きのハンドルを渡しただけでは、前者が後者へ変わるわけではない。相手が同じアドレス空間を自由に書き換えられるなら、相手の契約違反で内部のメモリ安全性も壊れうる。

### 2.3 仮定を、システムの主張として表す

```text
条件付きの接続:
  内部の検証 + 外部契約A
      ⇒ 接続したシステムの安全性

保護された接続:
  内部と境界機構の検証 + 実行基盤の前提
      ⇒ 境界が許す任意の外部の振る舞いに対する、内部の安全性
```

「外部世界以外は保証したい」が、外部の契約違反にも耐えるという意味なら、後者を要求する必要がある。unsafeで契約を引き受けるだけでは、その強い要求を満たさない。

## 3. 宣言・接続・利用の三段階に分ける

### 3.1 宣言: 必要な外部契約を書く

契約の宣言位置に、呼び出し規約、領域の権限、保持する期間、コールバックなどの条件を集める。

```text
外部契約 DecoderContract:
  操作: decode

  内部側が満たす条件:
    入力と出力の領域は生存し、必要な範囲を確保している。
    呼び出し中、出力への排他的な権限を渡す。

  外部側に要求する条件:
    宣言したABIに従う。
    渡したホスト側の領域へのアクセスは、指定した範囲と権限を守る。
    呼び出し後に、その領域へのアクセスを残さない。
    この契約にないコールバックやスタック巻き戻しを行わない。

  戻り値:
    検証前の書き込み数と、状態コード
```

契約を書いたこと自体は、相手が守る証拠にならない。ここでは、内部が確認する義務と、外部の振る舞いについて必要になる条件を分けている。

### 3.2 接続: 特定の実装や装置へ結び付ける

次に、契約と実物を結び付ける。

```text
接続 decoder_native:
  契約: DecoderContract
  対象: 指定したライブラリ成果物、ABI、設定
  根拠:
    内部のアダプターは検証済み。
    外部側の契約遵守は、未検証の信頼として受け入れる。
  発行するもの:
    この接続に限定されたDecoderSession
```

unsafeに相当する宣言を置くなら、この「未検証の信頼として受け入れる」の部分になる。

相手の契約遵守を証明できた、または隔離機構によって必要な制約を強制できるなら、その条件については未検証の信頼を外せる。ただし、契約の各条件で根拠が異なることもあるため、接続全体を一個の「安全」フラグだけで表さないほうがよい。

### 3.3 利用: 権限付きのAPIとして呼び出す

内部コードは`DecoderSession`を通じて操作し、通常の型・状態・効果の規則に従う。

接続の利用者が毎回、ABIや相手のポインタ保持について同じ説明を繰り返す必要はない。一方、特定のバッファをその期間だけ渡すことなど、個々の呼び出し側の義務は、型や検査で満たす必要がある。

このAPIが安全と言える範囲も、2節の区別に従う。未検証の相手へ直接接続する場合には、接続全体の保証は外部契約を前提とする。

## 4. 外部契約には、何を記述するか

### 4.1 引数と戻り値の型だけでは足りない

| 契約の項目 | 記述する内容の例 |
| --- | --- |
| 表現と呼び出し | ABI、サイズ、アラインメント、値の表現、戻り方 |
| 読み書きの範囲 | 読める領域、書ける領域、内部の他の領域へ干渉しない条件 |
| 所有の移譲 | 借りるのか、所有権を渡すのか、誰が解放するのか |
| 保持する期間 | 呼び出し中だけか、明示した非同期処理の完了までか |
| 初期化 | どの範囲に、どの型として有効な内容を用意するか |
| コールバック | 呼び出せる関数、実行スレッド、回数、保持期間 |
| 再入と並行性 | 同時に呼べるか、呼び出し中に再び入れるか |
| 中断と失敗 | 例外、キャンセル、部分的な完了、エラー時に残る状態 |
| 実行環境 | 装置の種類、設定、マッピング属性、同期の規約 |

最初からすべてを複雑な記述にする必要はない。たとえば「同期的な呼び出しで、保持もコールバックもしない」を一つの基本形にできる。ただし、その基本形も契約として定義されている必要がある。

### 4.2 利用者側の条件と、相手側の条件を混ぜない

内部の型システムが、渡すバッファの排他性を確認しても、外部コードがポインタを勝手に保存しないことまで確認したことにはならない。

逆に、外部が領域を正しく扱うと仮定しても、内部が解放済みのバッファを渡してよいことにはならない。今回の仮定では、内部側の義務は検証し、外部側で証拠を持たない条件だけを信頼として残す。

### 4.3 観測した結果と、持続する条件を区別する

「今、完了フラグが立っている」という観測と、「この後、装置はそのバッファへ一切アクセスしない」という条件は別である。

後者を導くには、そのフラグの意味、メモリ可視性、処理中のアクセスが残らないことなどの契約が必要になる。型へ取り込む状態遷移は、こうした契約と対応させる。

## 5. 利用は、権限と状態の操作として表す

### 5.1 接続のハンドルは、利用できる対象を限定する

内部の関数へ任意の外部操作を許す代わりに、特定の接続のハンドルを渡す。

```text
decode_image(session: DecoderSession, input: Bytes) -> Result<Image>
read_sensor(sensor: SensorSession) -> Result<Sample>
start_dma(channel: DmaChannel, buffer: OwnedBuffer) -> InFlightTransfer
```

実際に共有できるか、消費するか、一時的に借りるかは、操作ごとの型で定める。この方法なら、接続を持たない関数へ、暗黙に外部への権限を与えずに済む。

ただし、**権限を表すハンドルは、相手が契約を守る証明ではない。** 誰が利用できるかと、利用した相手がどう振る舞うかは、別の条件である。

### 5.2 非同期の接続では、権限を持ち続ける主体を表す

外部が後からメモリやコールバックへアクセスするなら、一回の関数呼び出しの範囲に閉じない。

```text
OwnedBuffer
    ──送信開始──→ InFlight<接続, Buffer>
    ──完了を確認──→ OwnedBuffer
```

処理中は、内部の別のコードが同じ権限を使えないようにする。単に「最初の呼び出しが戻ったから、借用も終わった」と扱うことはできない。

### 5.3 効果と信頼の前提も分ける

「ネットワークへ送信する」という効果と、「相手がメモリの規則を守ると仮定する」という信頼の前提は、別の性質である。

普通のネットワーク受信なら、内容を任意のバイト列として扱い、安全に解析できる。受信した数値や文字列の意味を信用しなくても、メモリ安全性は保てる。すべてのI/Oへ、接続先を信頼するunsafe宣言を要求する設計にはしない。

もちろん、そのI/Oを実現するOSやランタイムについて、実行基盤としての前提はある。どの層の相手を信頼しているかを混ぜないことが重要である。

## 6. 例: 外部デコーダを接続する

### 6.1 直接呼び出す方式

内部で所有する入力と出力バッファを、同じプロセスの外部ライブラリへ一時的に渡す場合を考える。

```text
1. 出力用のバイト領域を確保し、内部で初期化する。
2. 型で確認した権限と範囲を、接続層へ渡す。
3. 外部のdecodeを呼び出す。
4. 戻った書き込み数が出力容量内かを検査する。
5. その範囲を、通常の安全なパーサーでImageへ変換する。
```

内部の変換を検証すれば、不正なサイズや画像形式を拒否できる。しかし、外部関数が3の実行中に領域外を書き換えた場合、4でサイズを検査しても、その破壊は取り消せない。

この方式で残るunsafe相当の責任は、外部の契約遵守を受け入れた接続点にある。利用コードからunsafeが消えても、システムの安全性はその契約を前提とする。

### 6.2 隔離して呼び出す方式

同じデコーダを、分離したメモリを持つ実行環境へ置く方式も考えられる。

```text
1. 入力を、境界が管理するバイト列として渡す。
2. デコーダは、隔離先のメモリで処理する。
3. 境界機構を通じ、長さと範囲を確認して結果を取り込む。
4. 取り込んだバイト列を、安全なパーサーでImageへ変換する。
```

このとき、外部の生ポインタを、そのまま内部の参照にしないことが重要になる。共有メモリを使う場合も、変更されうる内容を、検査後に不変になったかのように扱わない。コピー、所有の移譲、アクセスの排他など、検査後の条件も維持する。

必要な境界を強制できるなら、デコーダ自身のメモリ安全性を信頼せず、内部を保護する方向へ進める。RLBoxは、隔離と境界を越える値の扱いを組み合わせる実例である。[RLBoxの原論文](https://www.usenix.org/conference/usenixsecurity20/presentation/narayan)

この場合も、内容が正しい画像であること、処理が必ず完了することなどは、別に保証する性質である。

## 7. 例: DMAの接続は、時間をまたぐ契約になる

### 7.1 内部が検証できる状態遷移

```text
Ready<Buffer>
    ──装置へ渡す──→ Active<Device, Buffer>
    ──停止と可視性の条件を確認──→ Ready<Buffer>
```

内部の検証では、`Active`の間はCPUへバッファの利用権限を返さないこと、同じ権限を複製しないこと、返却後だけ次の処理へ進むことなどを扱う。

### 7.2 接続で引き受ける条件

```text
HW-1: 指定した設定と領域に従って、装置がアクセスする。
HW-2: 指定した完了手順の後には、バッファへの装置のアクセスが残らない。
HW-3: 指定した同期手順で、必要な書き込みがCPUへ見える。
```

このような装置の契約が、型の状態遷移を実際の機械へ結び付ける。TockのDMA抽象化にも、バッファの受け渡しを表す仕組みと、アーキテクチャに依存する責任の分離が見られる。[TockのSafe DMA](https://tockos.org/blog/2026/talking-tock-63/)

ただし、上の`HW-1`などは本メモの整理であり、Tockがこの形式の契約を実装しているという意味ではない。

### 7.3 タイムアウトしても、権限は自動で戻らない

タイムアウトは、一定時間内に完了を観測できなかったという事実であり、装置がアクセスをやめたことの証明ではない。

安全性を保つためには、停止を保証する手順を実行する、装置のアクセスを実際に遮断して処理中のアクセスも終わらせる、返却せず領域を保留する、などの設計が必要になる。返却する条件が満たされないのに、エラーを返してバッファを再利用してはいけない。

これは、例外やキャンセル、ハンドルの破棄にも当てはまる。後始末が必ず実行されることだけに依存せず、実行されなかった経路でも、外部が使う資源を内部が早期に回収しない必要がある。

ここで、バッファを保留できても、装置が無関係なメモリへ書けるなら、その暴走までは防げない。契約違反にも耐える保証を求めるなら、メモリへのアクセスを制限する実行基盤も必要になる。

## 8. 契約違反を検出できることと、内部を守れることは違う

### 8.1 検出できる異常は、通常の値として扱う

不正な長さ、未知の状態コード、切断、応答の失効などは、検証できる表現へ取り込み、エラーや状態遷移として扱う。

外部から受け取る段階では、内部の強い型の条件を、まだ満たしていないものとして扱う。任意のビット列を、検査前から有効な参照や列挙型の値として生成してしまい、その後で確認する設計は避ける。

### 8.2 検査より前に破壊できる相手は、検査だけでは封じ込められない

領域外への書き込みや、返却後のポインタ利用は、単に戻り値を`Result`にするだけでは防げない。

この種の条件については、相手を検証する、実行環境で制限する、契約を信頼する、といういずれの根拠を選んでいるかを明示する必要がある。

WebAssemblyのように、メモリアクセスや外部への操作の境界を実行環境で制限する方式は、強制する側の設計の参考になる。ただし、その保証の単位と、ホストが提供する操作の正しさは区別する。[Wasmtimeのセキュリティモデル](https://docs.wasmtime.dev/security.html)

### 8.3 契約には、失敗した後に許される状態も含める

```text
成功:
  所有を取り戻し、結果を検証して通常の処理へ進む。

失敗したが、外部のアクセス停止を確認できた:
  資源を取り戻し、内容は未確定として処理する。

失敗し、外部のアクセス停止を確認できない:
  資源を通常の利用へ戻さず、接続と資源を保留・隔離する。
```

どの状態が可能かは接続ごとに違う。形式上エラーが返ることだけで、すべての権限や資源を元へ戻せるとはしない。

## 9. 信頼の依存関係を、どう管理するか

### 9.1 接続の宣言と、影響範囲は別に追う

信頼を宣言する場所を一か所に集めても、その条件が破られたときの影響が、その一か所に収まるわけではない。

同じプロセスの外部コードを信頼しているなら、その依存はプログラム全体のメモリ安全性へ影響しうる。型付きのラッパーで包んでも、その履歴が消えるわけではない。

したがって、呼び出し側へ毎回unsafeを付ける代わりに、ビルドや接続設定から、推移的な依存を一覧できる形がよいと考える。

```text
この構成の安全性に必要な未検証の外部条件:
  decoder_native.ABI_and_memory_contract
  board_dma.device_contract

実行基盤として依存するもの:
  選択したOS・隔離機構・機種の仕様
```

### 9.2 相手の識別と、契約が正しい証拠を分ける

ライブラリのバージョン、成果物のハッシュ、ABI、装置の種類や設定は、「何に接続したか」の記録になる。

しかし、識別できることや署名があることだけでは、その相手がメモリの契約を守る証明にならない。識別情報と、その対象について何を検証・確認・仮定したかを分けて記録する。

### 9.3 更新時は、契約と根拠の対応を確認する

相手の更新や設定変更で、保持期間、コールバック、初期化、失敗時の状態が変わることがある。通常の関数の型が同じでも、安全性に必要な条件は変わりうる。

設計案としては、契約と対象の組を識別し、対象が変わったら以前の信頼の宣言や証明を無条件には再利用しない。互換性を確認した範囲、または新たな根拠を要求する。

## 10. unsafeという構文は、どこに残るか

### 10.1 主な置き場所は、接続の宣言か設定になる

私は、次のような構成に落ち着くと考える。

| 場所 | 主な役割 | 未検証のunsafe相当の宣言 |
| --- | --- | --- |
| 通常のアルゴリズム | 型・権限・証明に従って値を処理する | 不要 |
| 検証された接続アダプター | 表現、範囲、所有、状態を変換する | 内部の変換については不要 |
| 外部契約の宣言 | 相手へ要求する振る舞いを定義する | 宣言だけでは、信頼したことにしない |
| 実装・装置への接続 | 必要な条件の根拠を指定する | 証拠や強制がない条件を引き受ける場合に置く |
| 起動・配備の設定 | 契約と、実際の対象や実行環境を一致させる | 対象・設定について残る前提を記録する |

起動時の処理として実行される場合もあるが、意味は「この行から任意の内部規則を破ってよい」ではなく、「この条件の下で外部接続を導入する」である。

### 10.2 一般的なunsafeブロックを、残す必然性は薄くなる

今回の仮定では、内部の低水準操作を正当化するための抜け道は不要である。検査できない条件を、外部との接続に限定して受け入れる仕組みがあればよい。

名前は`unsafe`のままでも、`trusted external`などでもよい。キーワードの選択より、対象・契約・引き受ける条件・利用権限を限定できることが重要である。

### 10.3 接続を利用する層では、構文が消えてもよい

利用者が、選択された接続の権限を受け取るだけなら、アプリケーションにはunsafe構文が一切現れない設計も自然である。

ただし、未検証の外部条件がある構成なら、それが消えたと説明してはいけない。ソースの各所で引き受ける方式から、接続時に引き受け、依存を記録する方式へ変わったのである。

## 11. この方式を成立させるための条件

### 11.1 任意の事実を信じる抜け道へ戻さない

外部契約を導入する仕組みが、任意の内部命題を無条件に真とする`assume`としても使えるなら、内部を保証するという前提が崩れる。

契約は、特定の外部操作・資源・環境の振る舞いと結び付ける。利用する内部コードも、契約が与える範囲を越えた権限や事実を導けないようにする。限定した契約でも、虚偽なら条件付き保証は失われるため、宣言の形を制限するだけで証拠になるとは考えない。

### 11.2 権限の発行と、接続の差し替えを管理する

どのコードでも任意の実メモリの所有権を宣言したり、検証済みの接続先を未検証のものへ黙って差し替えたりできれば、境界を限定できない。

接続を作るコードや配備設定の役割と、接続を使う通常のコードの役割を分ける。必要なら、特定の境界を追加する権限そのものも、明示的に渡す。

### 11.3 外部の状態を、内部へ取り込む変換も検証する

相手に契約を要求しても、受け渡しのアダプターが、範囲を取り違える、失効したハンドルを使う、異なるアロケータで解放する、といった誤りを起こせば安全ではない。

今回の仮定では、そこを新しい未検証の内部コードとして残さず、検証する側へ含める。外部の責任を狭くするために、表現の変換や権限操作を内部側できちんと引き受ける。

この文書の「契約・接続・利用」の構成全体は、本メモの設計案である。以下の機能や研究が、そのまま同じ仕組みを実装しているわけではない。

新しい言語機能、証明、処理系の実装は行っていない。この方式でどこまで静的な保証を与えられるかは、具体的な契約言語と実行モデルを定義して検証する必要がある。
