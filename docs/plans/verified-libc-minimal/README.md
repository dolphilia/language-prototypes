## 1. 何を作り、何を確かめるか

**AArch64向けの`memcpy`と`memset`の2関数を作り、実際の機械語についての証明を検査し、Cから呼んだ実物との対応を確認する。** さらに、`memcpy`に一つだけ高速経路を加え、証明・速度・容量の変化を比較する。

新しく作るのは、2関数、小さな命令マクロ、証明スクリプト、成果物を照合する処理、試験・計測用のコードに限る。証明の中核、完全なISAモデル、汎用アセンブラ、独立した新言語は作らない。

確認したい仮説は三つある。

1. **証明と実物がつながる:** 数学的な仕様、命令列、オブジェクト、リンク後の関数本体まで、一つの検査手順で追える。
2. **小さな抽象化を再利用できる:** コピーや書き込みの命令マクロを、根拠のない公理を足さず、既存の命令の意味と定理から構成できる。
3. **証明のための実行費用を増やさない:** 証明やghostデータを実行コードへ含めず、最適化前後の速度・コードサイズを実物で比較できる。

「2関数の検証経路が完成した」と「システムlibc以上の性能を達成した」は別に判定する。性能が未達なら、その結果を記録し、性能まで達成したライブラリとは呼ばない。

## 2. 最初の対象と、対象外

### 2.1 公開する関数

既存libcを差し替えず、試作専用の名前で公開する。

```c
#include <stddef.h>

void *vp_memcpy(void *dst, const void *src, size_t n);
void *vp_memset(void *dst, int c, size_t n);
```

| 関数 | 仕様 | 最初の実装 |
| --- | --- | --- |
| `vp_memcpy` | 非重複の領域へ開始時点の入力の`n`バイトをコピーし、元の`dst`を返す | 1バイトずつコピーするループ |
| `vp_memset` | `c`をunsigned char相当へ変換した値で`n`バイトを埋め、元の`dst`を返す | 1バイトずつ書き込むループ |

仕様では、`memset`の書き込み値を`c mod 256`として扱い、負の`int`も含める。サイズは固定長や試験範囲だけに制限せず、**事前条件を満たす任意の`size_t`値**について証明する。

### 2.2 共通の事前条件と境界

- 対象は通常のRAM。必要な読み書き権限が呼び出し中維持され、他スレッドによる変更・解放やMMIOを扱わない。
- 領域はアドレス空間内に収まり、必要なアドレス計算が折り返さない。書き込み先は実行コードと重ならない。
- `vp_memcpy`は入力・出力の非重複を要求する。同一アドレスの特例も、この版の公開契約へは含めない。
- `n == 0`ではデータメモリにアクセスせず、元の`dst`を返す。ただし、公開する呼び出し条件はNULLではないポインタに限定し、NULLとゼロ長の組み合わせは今回のAPI契約に含めない。
- ABI上の保存レジスタとSPを保存し、X30に与えられた戻り先へ戻る。スタック・ヒープを使わない葉関数とする。

この契約を明示した試作であり、C規格の全要件や、コンパイラがfreestanding環境へ要求する全条件を満たすlibcとしては扱わない。Cヘッダーと機械語のABI接続は試験するが、CコンパイラやC呼び出し側全体の形式検証は行わない。

### 2.3 今回は扱わないもの

`memmove`、`memcmp`、`strlen`、アロケータ、浮動小数点、スレッド、動的リンクによる差し替え、CPU別の自動選択、SIMD、暗号用途の定数時間性、Rust向けの安全なラッパーは対象外とする。両関数が完成するまで関数を増やさない。

## 3. 実装基盤を一つに決める

### 3.1 対象環境と再利用する基盤

| 項目 | 採用方針 |
| --- | --- |
| 対象 | macOS / arm64、リトルエンディアン、Appleプラットフォームの通常のarm64呼び出し。arm64eは対象外 |
| 成果物 | arm64単独のMach-Oオブジェクトと、それを静的に組み込んだ試験用実行ファイル |
| 機械モデルと証明 | HOL Lightと、s2n-bignumのAArch64モデル・実行／証明用の補助処理を再利用 |
| アセンブルとC側 | Clang系の処理系。利用する実行形式・SDK・リンク構成は最初の環境確認で固定 |
| 補助処理 | OCamlで命令マクロと証明、Python 3で成果物の照合と結果の集約、Makeで順序を管理 |
| 依存の管理 | 動作確認したHOL Light、s2n-bignum等のコミットと導入手順を記録。検査時に最新版へ自動更新しない |

計画作成時の読み取り確認では、ホストはDarwin/arm64で、Clang、OCaml、opam、Python 3、Make、LLVMのオブジェクト操作用ツールが見つかった。HOL Lightとs2n-bignumの導入状態・組み合わせの動作は未確認であり、次節のP0で確認する。

この選択は、対象機器で直接動かしながら、機械モデルを作り直す範囲を避けるためである。s2n-bignumの共通読み込み処理にはMach-Oオブジェクトを扱う経路があり、既存の証明には実物の命令列との照合例がある。ただし、**リンク済みのMach-O実行ファイルまで同じ読み込み処理で扱えるとは仮定しない**。[共通のオブジェクト読み込み処理](https://github.com/awslabs/s2n-bignum/blob/main/common/elf.ml)、[AArch64証明の例](https://github.com/awslabs/s2n-bignum/blob/main/arm/proofs/bignum_add.ml)

### 3.2 最初に通す確認

P0では、既存の小さな証明例の再検査と、試作用の`ret`だけの関数を用いて、次を確認する。

1. 固定した依存を読み込んだ新しいHOL Lightプロセスで、期待する定理を作れる。
2. ネイティブのMach-Oオブジェクトの命令列を、既存の読み込み経路で照合できる。
3. 同じ関数をCから呼び、リンク後の関数本体の位置とバイト列を抽出できる。
4. 命令バイトを変えると照合が失敗し、証明の例外や未完了を成功扱いしない。

ここが通るまでは、関数実装や汎用マクロへ進まない。Mach-Oの取り込みが合わない場合は、この小さな確認だけで原因を切り分け、対象の限定や補助処理の変更を計画へ記録する。別の形式の成果物の証明を、ネイティブ成果物の証明として代用しない。

## 4. 最低限必要な証明

各版の各関数について、次の三種類を明示して証明する。証明は呼び出し条件を満たす全状態に対するものであり、試験した入力の列挙ではない。

| 証明 | 内容 | 予定する定理名の例 |
| --- | --- | --- |
| 機能と終了 | コピー／埋め込みの結果、戻り値、戻り先への有限ステップでの到達 | `VP_MEMCPY_CORRECT`、`VP_MEMSET_CORRECT` |
| 保存状態と資源 | 許したレジスタ・出力領域以外を保存。SP不変、スタック・ヒープ使用ゼロ | 上の定理の変更範囲と、必要な補題 |
| アクセス範囲 | 実行途中も、読み書きが許可された入力・出力範囲内に収まる | `VP_MEMCPY_ACCESSES`、`VP_MEMSET_ACCESSES` |

アクセス範囲にはs2n-bignumのイベントと範囲の定義を使う。最終状態の`MAYCHANGE`だけで、途中の読み取りまで安全と判断しない。命令フェッチとデータアクセスも区別する。[既存のアクセスイベントと範囲の定義](https://github.com/awslabs/s2n-bignum/blob/main/common/safety.ml)

ループでは、処理済みの長さ`i`、`0 <= i <= n`、出力の先頭`i`バイトの仕様、入力と未処理領域の保存を不変条件とし、`n - i`の減少で終了を示す。戻り値に使う元の`dst`も保存する。実行時間の秒数や全CPUでの定数時間性は、この終了の証明へ含めない。

ABIの接続では、`memset`の`int`引数に必要なビットだけを条件にし、上位ビットが特定の拡張方法で埋まることを勝手に仮定しない。使用する一時レジスタと変更範囲を固定し、Appleプラットフォームで予約・保存される状態を壊さないことを確認する。

公開契約は、マクロ展開器とは独立した`proofs/specs.ml`に定義する。コードの都合で前提を増やしたり、結果の条件を弱めたりした場合に、同じ契約を証明したことにしない。新しい実装の正しさを`new_axiom`などで仮定することは禁止する。証明中の通常の仮定の導入と、未証明の公理の追加は区別する。

## 5. マクロと生成処理の最小構成

独自パーサーは作らず、固定した少数の命令を並べるOCaml側の小さな構造と、証明を組み立てる補助関数を用意する。レジスタの自由な割り当てや最適化探索は行わない。

| 部品 | 用途 | 証明すること |
| --- | --- | --- |
| `CopyByte` | 1バイトのロードとストア | 入力バイトのコピー、読み書きの範囲、破壊する一時レジスタ |
| `FillByte` | 指定した1バイトを書き込む | 書き込みの結果と範囲、保存状態 |
| `Copy8` | 後述の一つだけの高速経路 | 整列済みの8バイトのロードとストアが同じコピー仕様を満たす |

各マクロは、命令列と対応する定理を組にして扱う。証明の根拠は再利用する命令の意味と定理であり、マクロ名を信頼済み操作として登録するだけにはしない。生成されたアセンブリをアセンブルした後に、その命令バイト列も照合する。

証明用の値や権限はHOL Light側に置き、実行コードへ出力しない。マクロの誤展開、レジスタの取り違え、命令の変更は、命令列の照合または契約の証明で拒否される構成にする。

## 6. オブジェクトと、リンク後の実物を照合する

初期版では、**1関数1オブジェクト、外部呼び出しなし、定数表なし、コード領域の再配置なし**に限定する。内部の分岐は同じ関数内で完結し、任意の適切に整列した配置先に対して証明する。

検査の流れは次のようにする。

```text
公開仕様＋命令マクロ
  → アセンブリ
  → Mach-Oオブジェクト
  → 命令バイト列を取り込んで照合し、関数の定理を検査
  → 試験用実行ファイルへリンク
  → 対象シンボルの関数本体を取り出し、証明したバイト列と比較
  → Cからの試験、速度・容量の測定
```

リンク後は、対象シンボルの一意性、実行セクション内の範囲、関数本体の長さと全バイトの一致を確認する。単一arm64のMach-Oだけを受理し、非対応の形式・再配置・外部参照は成功扱いしない。LTOや関数本体を書き換える後処理は、この構成へ含めない。

リンク済みファイルの抽出には、まず手元のオブジェクト操作用ツールを使えるかP0で確認する。必要なら、固定したMach-O形式のセクション・シンボル・バイト範囲だけを読む小さな補助処理を作る。抽出処理と既存ツールによる表示を比較し、位置・長さの誤りを検出する試験を用意する。この抽出部分は未検証の信頼基盤として記録する。

命令列の期待値を変更した場合は、機能とアクセスの証明を再実行する。ハッシュや期待値ファイルの更新だけで受理しない。リンク後の対応は、この版では**検証されたリンカによる定理ではなく、未検証の抽出・比較処理による確認**である。

## 7. 実装の順序と成果物

| 段階 | 作業 | 成果物と通過条件 |
| --- | --- | --- |
| P0: 接続を先に試す | 依存を固定し、既存証明と`ret`だけの試作でMach-Oからネイティブ実行までを確認 | 環境記録、依存の固定情報、取り込み・リンク後照合の最小例。3.2節の全項目が通る |
| P1: 契約と最小部品 | 2関数の契約、`CopyByte`・`FillByte`、生成と証明の補助処理を作る | 公開契約の定義、部品の定理。正当な呼び出し例を構成でき、条件が空虚でないことも確認 |
| P2: 基本版2関数 | バイトループを生成し、終了・保存状態・アクセスを証明 | 基本版の2関数と定理。事前条件を満たす任意の長さを扱い、ゼロ長のアクセスなしも確認 |
| P3: 実物と接続 | 基本版をCから呼び、リンク後の対応と境界の試験を行う | 試験用実行ファイル、照合記録、試験結果。未検証の外部呼び出しが関数本体にない |
| P4: 一つだけ最適化 | `vp_memcpy`に、長さが8で両アドレスが8バイト整列した場合の`Copy8`経路を加える。他は基本版へ進む | 最適化版の同じ公開契約の証明。8バイト読み書きと条件分岐の正当性を確認 |
| P5: 測定と判定 | 基本版・最適化版・システムlibcを同条件で測り、容量と残る信頼をまとめる | 再実行手順、測定値、達成／未達の判定、残課題の記録 |

P4でも追加の余白や、常に整列していることを公開APIの前提に加えない。高速経路の条件は関数の入口で確認し、未整列や他の長さでは基本版を使う。SIMDや汎用の8バイトループへは広げない。

日数を固定する代わりに、各段階の通過条件で進める。特にP0とP2で見つかった依存・証明の難しさを記録し、次の範囲を増やさない。性能が未達でも、今回の計画を際限のない最適化作業へ変えず、P5で結果を明確に判定する。

## 8. 予定する配置と実行手順

実装は、既存の試作言語から独立した`prototypes/verified-libc-minimal/`に置いた。以下は計画時に想定した配置であり、実際のファイルと使い方は[実装のREADME](../../../prototypes/verified-libc-minimal/README.md)を参照する。

```text
prototypes/verified-libc-minimal/
  README.md                 # 導入・検査・測定・保証範囲
  Makefile
  deps.lock                 # 依存コミット、導入に必要な版と構成
  include/vp_memory.h        # 2関数のC宣言と呼び出し条件
  generator/                # 少数の命令と3つのマクロ、アセンブリ出力
  proofs/specs.ml            # 公開契約
  proofs/macros.ml           # マクロの証明と合成用の補助処理
  proofs/memcpy.ml           # 基本版・最適化版の証明
  proofs/memset.ml
  tools/                    # 証明の実行、成果物照合、結果の集約
  tests/                    # Cの境界試験、ABI確認、意図した破壊の試験
  benchmarks/               # Cの計測用コード
  reports/                  # 測定条件・結果・信頼基盤の短い記録
  build/                    # 生成アセンブリ・オブジェクト等。Git管理外
```

依存の導入は明示した手順で行い、通常の検査コマンドからネットワークへアクセスしたり、依存を自動更新したりしない。既存プロジェクトのモデルと証明補助処理を利用し、暗号ライブラリ全体の構築・検証を必須にしない。再利用部分のライセンスと出典を残す。

導入後の利用者向け入口は、次の二つである。いずれも実装し、`measure`による全検査と測定の完走を確認した。

```sh
# 実施結果と保証の範囲は、冒頭の完了監査を参照。
make -C prototypes/verified-libc-minimal verify
make -C prototypes/verified-libc-minimal measure
```

`verify`は生成、証明の新規プロセスでの再検査、オブジェクトとリンク後の照合、Cの試験、意図した破壊の拒否を実行する。`measure`は速度と容量を測り、条件と生の結果を保存する。検査済みの成果物が変わったら、測定を検査結果へ流用しない。

証明の実行はログに「成功」が含まれるだけでは判定しない。終了状態、期待する定理と命題の生成、実際の対象コードとの対応を確認する。失敗したプロセスの古い結果や、依存の違うキャッシュを成功扱いしない。

## 9. 検証・試験・測定で確認すること

### 9.1 Cからの試験

- 長さ`0, 1, 2, 7, 8, 9, 15, 16, 17, 31, 32, 63, 64, 255, 256`と、固定シードで生成した入力を調べる。
- 入出力の整列を変え、入力の保存、出力の内容、戻り値、領域前後の番兵を調べる。
- `memset`では`0, 1, 255, 256, -1, INT_MIN, INT_MAX`などの低8ビットへの変換を調べる。
- ガードページに接する有効な領域を使い、境界の余分な読み書きを検出する。ガードページの準備は試験用のOS依存処理として、検証対象の2関数から分ける。
- 小さな呼び出し用アセンブリで保存レジスタとSPを確認する。試験用コードは未検証であることを記録する。

比較対象も契約を満たす呼び出しだけにする。`memcpy`の重複領域やNULLを含む未対象ケースを、システムlibcとの同等性の根拠に使わない。Cによる単純な参照結果とシステムlibcの両方で確かめ、同じ実装へ自己比較する構成を避ける。

### 9.2 意図して壊した場合の拒否

| 壊す対象 | 検出する段階 |
| --- | --- |
| 1バイト余分に書く／読む命令へ変更する | アクセス範囲の証明。ガードページ試験も補助に使う |
| 戻り値、保存レジスタ、ループの終了条件を壊す | 機能・保存状態・終了の証明 |
| オブジェクトまたはリンク後の関数本体を1か所変更する | バイト列と長さの照合 |
| 高速経路を、長さが8未満の場合にも実行するように変える | 公開契約・アクセス範囲の証明 |
| 新しい未証明の実装仮定を追加する | プロジェクトの公理追加の検査とレビュー |
| 必要な定理を作らずに証明処理を終える | 証明実行用の処理 |

最初のバイト列照合を通過させるために期待値も更新した場合でも、壊れた実装の**証明が失敗する**ことを確認する。これにより、ハッシュの固定だけを検証と呼ぶ誤りを避ける。

### 9.3 速度と容量

基本版と最適化版は同じ公開契約を持ち、それぞれ独立した成果物として評価する。システムlibcとの比較も行うが、結果は観測した機器・構成の範囲に限る。

- 長さと整列ごとに、ウォームアップ後の独立した測定を少なくとも7回行い、中央値とばらつきを保存する。バッチ内の反復数は計測器の分解能に対して十分な時間になるよう基本版で調整し、各比較対象で同じ方法を使う。特に8バイト整列の長さ8と、分岐が増える他のケースを両方調べる。
- 呼び出しをインライン化・除去させず、実行後の結果を観測する。システムlibcの呼び出しがコンパイラの別の命令列へ置換されていないかも逆アセンブルで確認する。
- 関数本体の命令バイト数、整列用の余白、オブジェクトの容量、同じハーネスへ組み込んだ実行ファイルの容量を分ける。共有libcの全容量を2関数の容量と比較しない。
- 証明・ghost用の命令やデータ、外部への補助呼び出しが関数本体に残っていないことを確認する。

自作の実行部分を小さく保つ目安は、**選択した版の2関数の命令本体の合計256バイト以下、スタック・ヒープ使用ゼロ**とする。これは実装前の設計目標であり、測定済みの値ではない。証明環境や既存ISAモデルの大きさとは分けて数える。

速度の判定方法・繰り返し条件は、最適化版の結果を見る前に固定する。ばらつきで結論が変わる結果は「不明」とする。基本版より速くてもシステムlibcより遅ければ、その差を隠さず「システムlibc比では未達」と記す。

## 10. 完了条件と、残る信頼

### 10.1 プロトタイプとしての完了条件

次をすべて満たした時点で、この計画の実装を完了とする。

1. 2関数の基本版と、`memcpy`の一つだけの最適化版があり、公開契約を満たす。
2. 必要な機能・終了・保存状態・アクセスの定理を、固定した依存で再検査できる。
3. Cから使う実行ファイル内の関数本体が、証明対象と一致することを確認できる。
4. 境界・ABIの試験と、意図した破壊の拒否が通る。
5. 対象機器の速度・容量を測り、基本版・最適化版・比較対象の結果を残す。
6. 実行時の証明用処理がなく、容量・資源の目標を満たす。未達なら完了条件の変更で隠さず、計画に対する未達として記録する。
7. 導入・再検査・測定の手順、前提、未検証部分がREADMEと報告にある。

性能の報告では、別に「基本版比」「システムlibc比」「サイズ増加」「証明用オーバーヘッド」の判定を載せる。すべてを一個の成功フラグへまとめない。実測の高速化を達成できなくても、その事実を示した検証・評価の試作は作れるが、「速度・容量で妥協のない実用libcを完成した」とは報告しない。
